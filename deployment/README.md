# V1-OPS encrypted file deployment

This is a local encrypted file backend, not an external KMS acceptance result. It requires a separately provisioned 32-byte root key, held outside the image, repository, PostgreSQL, Redis and ciphertext backup. The deployment operator owns the root key recovery copy and its access control.

Provision the host key directory with mode `0700` and ownership matching UID 1000 inside the app containers. Write `<key-id>.key` as 32 random bytes encoded with base64url, mode `0600`; write `current` containing only that key ID, mode `0600`. Mount the directory read-only as `DGOS_ROOT_KEY_HOST_DIR`. Never put key material in `.env`, Compose variables, or a backup archive. Provision a separate PostgreSQL password file for `DGOS_POSTGRES_PASSWORD_FILE`. Set `DGOS_DATABASE_URL` to the same database credentials with a non-default password, `DGOS_PUBLIC_HOST` to a DNS name, and `DGOS_PUBLIC_ORIGIN` to its `https://` origin. Provision a nonempty JSON array of operator package trust roots and mount it read-only using `DGOS_PACKAGE_TRUST_ROOTS_HOST_FILE`; the file must be readable by UID 1000. The `package-data` volume persists package bytes and is initialized with UID 1000 ownership. Missing roots or package storage fail production startup.

The production Compose exposes only the Caddy HTTP/HTTPS entry. Caddy obtains certificates for the configured DNS name. The app containers use an encrypted ciphertext volume; Redis is disposable. `scripts/v1-ops-api.mjs` and `scripts/v1-ops-worker.mjs` inject the same durable Secret service and a PostgreSQL backed audit sink. The API readiness hook checks the root key, ciphertext directory, PostgreSQL and Redis. The image build invokes the D Web `build` script and requires `apps/web/dist/index.html`. `DGOS_EXTENSION_CONFIG_FILE` points to the included reviewed V1 runtime profile for both API and Worker; replacing it requires an operator-reviewed, image-contained file. The current r11 release evidence and blockers are recorded in [V1-OPS-SECURITY-CLOSURE-r11](../.herdr/V1-OPS-SECURITY-CLOSURE-r11.md).

The API has no published host port. Caddy is the only peer on the internal backend with fixed address `192.168.240.10`; API trusts only that `/32`, and Caddy overwrites Host, forwarded proto and forwarded host while removing forwarded port/SSL headers on `/api/*`, `/health`, and `/ready`. The gateway also joins the edge network; API and Worker join egress for controlled upstream requests. Check `192.168.240.0/24` against every target-host Docker network before creating the stack and update the subnet, gateway address and `DGOS_TRUSTED_PROXY_CIDRS` together if it overlaps. Keep `DGOS_PUBLIC_ORIGIN` equal to `https://DGOS_PUBLIC_HOST`.

The Linux image uses Node 22 trixie slim, installs Playwright Chromium headless shell and bubblewrap, and runs as UID 1000. API and Worker use `no-new-privileges`, drop all capabilities, and use `deployment/seccomp-bwrap.json`. This profile is Docker's default deny profile (source SHA-256 `6416b47770785a41ac59073cdc77d9fe98517df2799dc83ef207e622de3053f6`) plus user namespace `clone`/`unshare`, `mount`/`umount2`, and `pivot_root` rules needed by bubblewrap. Rebuild it only from that exact source with `node deployment/build-seccomp-profile.mjs DOCKER_DEFAULT.json NEW_PROFILE.json`; review any Docker engine/profile update before use. The default action remains `SCMP_ACT_ERRNO`. This local Docker Desktop proof does not certify another Linux host. Run the target-host runner file-write and network-denial probe before enabling stdio MCP.

## Backup and recovery

Stop API and Worker writes and reconcile pending provider/extension Secret intents, proxy provisioning and package staging before a consistent backup. Set `DGOS_OPS_MAINTENANCE_URL` to the `postgres` maintenance database, and `DGOS_OPS_PG_CONTAINER` to the PostgreSQL container in that same cluster. For a production operation, also set `DGOS_OPS_MODE=production`, `DGOS_OPS_AUTH_MAINTENANCE_URL` to the same exact maintenance URL, `DGOS_OPS_AUTH_PG_CONTAINER` to the same exact container name, and `DGOS_OPS_AUTH_SOURCE_DATABASE` to the reviewed source database. The matching authority variables are a deliberate operator assertion, not an approval mechanism. Run `node scripts/v1-ops-multistore.mjs backup SOURCE_DB PACKAGE_DIR CIPHERTEXT_DIR NEW_ARCHIVE_DIR --all-writes-stopped`. The script checks the exact source name, URL/container PG system identifier, pending intents and new archive path; it writes `pg_dump -Fc`, all package files, all encrypted Secret records, SHA-256 hashes and a database-reference digest manifest. The root key is never copied. The stop-writes flag cannot pause concurrent processes itself. Keep the independent root-key recovery copy and package trust roots under separate operator control. Without `DGOS_OPS_MODE=production`, the CLI is deliberately locked to the local `127.0.0.1:15310` random-database fixture.

In a fresh isolated restore environment, provision the root key directory independently. For production mode set `DGOS_OPS_AUTH_TARGET_DATABASE` to the reviewed new target database and retain the authorized source name matching the archive manifest. Run `node scripts/v1-ops-multistore.mjs restore ARCHIVE_DIR NEW_RESTORE_DB NEW_PACKAGE_DIR NEW_CIPHERTEXT_DIR KEY_DIR`. The target database and directories must be new, and the target cannot equal the source; the script only drops a target it created during this operation if validation fails. It checks the URL/container PG cluster identity, dump/file hashes, AES-GCM tags and PostgreSQL references, and leaves the result in `restored_read_only_validation_required`. Its internal Secret validation lock needs a writable isolated ciphertext directory. Keep writes disabled until service smoke and operator review pass. This generic engine was exercised in production mode against the isolated local fixture only; real production storage, permissions and rollback still need a target-environment rehearsal. If an abnormal stop left `.lock` directories, stop every API/worker process using the volume, then run `node scripts/v1-ops-clear-stale-locks.mjs CIPHERTEXT_DIR --all-processes-stopped` before reopening writes.

`node scripts/v1-ops-rehearsal.mjs` exercises the 15310 fixture with a random database, independent root key, one encrypted Secret and a signed-package-shaped file tree. Its measured recovery time is a local fixture observation, not an approved RPO/RTO objective or production restore result. A target deployment needs a scheduled consistent backup, storage retention, operator key recovery, target-host restore rehearsal and approved objectives.

## Rotation

With writes paused, run `node scripts/v1-ops-rotate.mjs CIPHERTEXT_DIR KEY_DIR NEW_KEY_ID`. It writes a new root key, switches the current pointer, then rewraps records. Repeat the command's `rewrap()` step through a service handle if interrupted after the pointer switch. Keep the old key until every old ciphertext backup has expired or been rewrapped and verified. This is a local disk exercise; production certificate, KMS and RPO/RTO evidence require separate deployment validation.

Existing format 1 ciphertext must be migrated offline before starting the production wrapper. Its `revoked` flag was not authenticated. Review each record's original control state against independent audit/history and prepare a JSON array of approved SHA-256 SecretRef file-name digests. With all processes stopped and a backup retained, run `node scripts/v1-ops-migrate-legacy.mjs CIPHERTEXT_DIR KEY_DIR REVIEWED_DIGESTS_JSON --offline-reviewed-legacy-state`. The migration increments version and authenticates all control fields in format 2. Unreviewed records remain unavailable.

## FR001 network route wiring

`src/security/network-route.mjs` exports `createNetworkRouteFactory({ egress, secretService, systemProxyProvider, proxyLookup, ca, proxyCa, allowLocalFixture })`. API and Worker construct one factory instance per process and use its `request({ url, method, headers, body, signal, timeoutMs, maxResponseBytes, streamResponse })` path for Provider connection tests, model refreshes, AI tasks, and MCP HTTP/online import. MCP endpoint profiles call `forEgress(scopedEgress)` so their declared host allowlist remains in force. `allowLocalFixture` is only for isolated test processes and must remain false in production.

Apply `0045-network-route-activation.sql` and `0048-network-route-fingerprint.sql` before starting this runtime. At process start, `SystemService.activateNetworkRoute(route, { role, instanceId })` reads the persisted network target and records an API or Worker instance acknowledgement. The route remains closed until its acknowledgement is committed. Instances renew a short lease and stop network requests if renewal fails or expires. System projection reports a route as effective only when API and Worker each have a live acknowledgement and **every** live instance uses the target network version and the same route fingerprint. A partial restart remains `effectiveRoute=unavailable`, `restartRequired=true`; an offline old instance expires instead of blocking forever. Activation and release changes that alter the public state increment `contextVersion` and write a network SSE event. Saving settings updates the target network version and leaves running process routes unchanged until restart.

For manual mode, `manualProxyRef` points to a Secret whose `purpose` is `network-proxy`, `subjectId` is `system`, and value is JSON `{ "url": "https://proxy.example:443/", "authorization": "Basic ..." }`. Provision that JSON through the Secret service's controlled write path, not a plaintext environment variable. The public PATCH verifies the SecretRef before saving. Every request resolves and reads a fresh short-lived Secret handle; revoke and version change stop requests until the next activation. For system mode, optional `DGOS_SYSTEM_PROXY_SECRET_REF` is a reference only; the referenced Secret has the same scope and JSON shape. An absent reference selects direct routing, whereas an unavailable configured reference blocks startup. Plaintext `HTTP_PROXY`/`HTTPS_PROXY` credentials are not consumed. For a real HTTPS proxy, supply its trust roots through `proxyCa`; `ca` governs target TLS separately. Both target and proxy DNS candidates are checked, connections dial validated IPs, CONNECT sends only the pinned target IP, and target TLS verifies its hostname. The local test uses an explicit HTTP loopback proxy and private target allowance only inside a controlled fixture.
