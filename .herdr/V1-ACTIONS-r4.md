## Implementation facts and exact Lead wiring

- `PermissionBroker.check` ignores request `declared`. Ordinary app declarations come from active approved/official signed package deployment manifest `permissions ∩ capabilityAllowlist`; absent install is `deny`. A stored `deny` always wins. `decide` and request resolution put decision, request transition, audit event and outbox into one PG transaction; injected audit failure rolls all back. A duplicate decision `requestId` returns its durable receipt only for the same fingerprint.
- `src/permissions/builtin-declarations.mjs` is the one server-owned declaration registry. Fixed `dgos.system`: `system.settings.read`, `system.settings.write`, `system.navigate`. Fixed `dgos.extensions`: `skill.read/install/manage/uninstall/execute`, `mcp.read/install/manage/uninstall/connect/execute`, `extension.run.read/cancel`. The `dgos.extensions` identity matches `ExtensionService` defaults; Skill/MCP official app UI routes are separate. The list makes a capability eligible for `ask`, never grants `allow` or bypasses `deny`.
- Public API `POST /permissions/check`, `POST /permissions/request`, and `PATCH /permissions` must use `new PermissionBroker({ repository, audit })`. This broker denies reserved app IDs regardless of caller body `declared` or installed name collision. Create a separate trusted instance with `createTrustedBuiltinPermissionBroker({ repository, audit })` in `src/actions/runtime.mjs` for server-owned System Action/Extension calls. Do not expose that instance directly to public permission routes. `ActionService.plan/execute` currently permit caller `appId` override; Lead must remove the override or force `appId=registry.get(actionId).ownerAppId` in the Lead-owned route/runtime path before using trusted broker. Candidate and settings paths must use that same trusted Action broker and the fixed registry owner, not the request body. Extension service can use trusted broker for its fixed `dgos.extensions` default, while invocation with a caller appId must use ordinary manifest-bound check.
- `createPackageActionLifecycle({ repository: new PostgresPackageActionRepository(pool), registry: actions.registry, handlers: serverOwnedHandlerMap, bindHandler: (actionId, handler) => actions.handlers.set(actionId, handler) })` returns `onActionsChanged` and `hydrate`. Pass `onActionsChanged` to G's `PackageService` callback. Call `await hydrate()` on both API and Action worker after core action registrations and before serving/claiming. Both processes must provide the same server-owned handler map. The callback validates against the current active package manifest, persists per-subject binding/version/digest, then refreshes Registry. A handler rechecks subject binding immediately before dispatch. Uninstalling one subject leaves another subject's binding live; mismatched package digest disables stale bindings. `ActionRegistry.hydrate` preserves persisted numeric `actionVersion` across processes, while declaration `version` remains semver.
- Manifest ActionDeclaration fields were mapped from FR-009's frozen example: `version`, `inputSchema`, `outputSchema`, one `requiredCapabilities` item, `risk`, `sideEffects`, `confirmation`, `idempotency`, `cancellable`, and server handler ID. The V1 manifest JSON schema currently leaves `actions.items` generic; this module enforces the required fields on registration. Unsupported handler IDs and excess capability claims fail closed.
