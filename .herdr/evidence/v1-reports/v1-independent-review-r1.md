## Blocking findings for Lead

1. **E: MCP transport crosses subject binding.** `apps/extension-runner/src/runner.mjs:10,13,45-50,60` keys its live connection Map solely by `extensionId`. `src/extensions/service.mjs:35,42,92,104,138-151,179` persists and checks installations by `subjectId`, but does not pass that subject to `connect`, `invoke`, or `disconnect`. Trigger: subject A connects extension ID X to endpoint/profile A; subject B installs the same ID X with endpoint/profile B and connects, or invokes after its own DB connection state becomes connected. The runner can reuse A's connection, so B's tool call can run against A's server; B's disconnect can close A's connection. Fix: bind live transport by subject plus kind, extension ID, install/version or immutable configuration identity, and make all three runner operations use that binding. Confirm with two subjects, same extension ID, distinct local MCP fixtures; verify no cross-call, catalog reuse, or cross-disconnect. This is a code-path isolation defect; no live exploit was executed.

2. **E: persistent `connected` state has no process recovery.** `src/extensions/service.mjs:99-110,141,173-179` saves `connected` and catalog in the repository, whereas `apps/extension-runner/src/runner.mjs:10-16` keeps transport only in process memory. After restart or request routing to another runner instance, a run is accepted/claimed against the saved state but `invoke` returns `connection_not_ready`; `process` records it as `handler_failed` (`service.mjs:186-190`). `connect` returns early when DB says connected (`:93`), so an operator cannot restore it through that path. Fix: reconcile persisted state with live transport before admission/claim, or reconnect with an attempt/version fence; expose a recoverable state and prevent false successful connection receipts. Verify connect, restart runner, submit, reconnect and invoke; repeat with two instances.

3. **G: disk pointer and deployment can diverge after process crash; recovery is not wired.** `src/apps/package-service.mjs:159-175,195-210` writes `prepared`, changes/removes disk pointer, then saves deployment. A hard kill after `switch`/`removePointer` but before `saveDeployment` leaves resources governed by the pointer while DB still describes the old deployment. `recover()` exists, but the observed `apps/api/src/package-routes.mjs:6-20` neither calls it nor enumerates installed pairs at startup; the existing `apps/api/src/server.mjs:163-174` still registers the legacy package lifecycle. The PostgreSQL advisory lock (`src/apps/postgres-package-repository.mjs:6-14`) serializes cooperating callers but the inner writes use `pool.query` outside its transaction (`:36-44`). Fix: choose one authoritative lifecycle in Lead integration, enumerate and reconcile deployments before serving resources/launch, and make recovery crash safe with operation state and audit. Verify kill at both pointer-to-DB windows, restart, recover, then compare pointer, deployment, actions, health, and audit.

4. **G/H: required audit is not atomic with successful state.** G `submit` and `review` mutate repository/store before standalone audit (`src/apps/package-service.mjs:130-143`); install/uninstall use compensating rollback after standalone audit (`:164-198`), which cannot cover a crash. H `ProviderService.setState/deleteAccount` changes DB and, for deletion, revokes the external secret before `writeAudit` (`apps/api/src/provider-service.mjs:18-19`). H config create/update/remove/policy similarly writes state before audit (`src/provider-config/service.mjs:6-13`). Trigger: inject `audit.record/writeAudit` failure or kill immediately after DB state/secret revocation. The request fails while state may already have changed without an event, conflicting with FR-014 AC01/AC03 (`docs/03-功能规格/V1/10-身份与治理/05-审计与管理员系统治理.md:45,173-175`). Fix: share a transaction with audit/outbox for DB changes; handle filesystem and Secret side effects through a recoverable operation with explicit reconciliation. Verify each named branch using an audit failure and a process kill; assert no unaudited success and idempotent retry.

5. **E: terminal run transition and audit can split.** `src/extensions/service.mjs:183-190` commits `succeeded`/`cancelled` before `run.finish` audit. If audit fails, catch attempts another transition from the now terminal state; the second transition returns undefined and the second audit may also fail. The caller sees an error while terminal state lacks its finish audit. `connect` likewise persists `connecting`/`connected` before start/finish audit (`:99-114`). Fix: append run event and outbox audit in the same repository transaction, or reconcile missing audit by stable event ID; keep audit errors outside handler error classification. Verify injected finish/start audit failures and inspect run state, sequence, event, audit, and retry behavior.
