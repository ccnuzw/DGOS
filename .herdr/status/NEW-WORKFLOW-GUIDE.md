# DGOS 新工作流程详解

**版本**: 2026-10-03 重置后  
**制定者**: Lead (新接管)  
**目标**: 解决之前7个包全阻塞的问题，用Wave快速迭代法推进V1

---

## 一、核心问题诊断

### 旧模式的致命缺陷

```
旧模式运行状态（2026-10-03前）:
┌─────────────────────────────────────────────────┐
│ 7个工作包同时进行                                │
├─────────────────────────────────────────────────┤
│ GAP-TEST-01        → rejected (根check失败)      │
│ GAP-SEC-01         → blocked (等凭据撤销)        │
│ GAP-WEB-BUILD-01   → ready (但没人整合)          │
│ GAP-WORKBENCH-01   → blocked (等Web)             │
│ GAP-CANDIDATE-02   → blocked (等Web+Workbench)   │
│ GAP-W1-01          → blocked (signed drift)      │
│ GAP-W1-02          → blocked (Web构建失败)       │
└─────────────────────────────────────────────────┘
                    ↓
           全部卡住，无法推进
```

**根本原因**：
1. **依赖链太长**：Web → Workbench → Candidate，一个失败全线停摆
2. **任务粒度过细**：7个小包，每个都有依赖，协调成本巨大
3. **验证滞后**：规定"所有Writer停止才Verify"，导致问题堆积
4. **目标不清晰**：不知道"做到什么程度算完成"
5. **完美主义陷阱**：想一次性做完所有12个FR + 所有测试

## 二、新模式：Wave快速迭代法

### 核心理念

```
新模式：Wave工作法
┌──────────────────────────────────────┐
│ Wave 1: 修复构建阻塞 (1周)            │
│   目标：能启动看到界面                │
│   包数：1-2个                         │
│   验收：本地能跑起来                  │
├──────────────────────────────────────┤
│ Wave 2: 核心演示路径 (2周)            │
│   目标：Provider→Task→Skill完整演示   │
│   包数：2-3个                         │
│   验收：有完整演示视频                │
├──────────────────────────────────────┤
│ Wave 3: 打包和文档 (1周)              │
│   目标：可分享的安装包                │
│   包数：1-2个                         │
│   验收：能给别人安装演示              │
└──────────────────────────────────────┘
```

### Wave vs 旧模式对比

| 维度 | 旧模式 | Wave模式 |
|------|--------|----------|
| **并行度** | 7个包同时进行 | 每Wave最多2-3个包 |
| **依赖处理** | 复杂依赖链，互相等待 | Wave内包之间无依赖或单向依赖 |
| **验证时机** | 所有Writer完成后 | 每个包完成立即验证（30分钟内） |
| **目标清晰度** | "修复所有问题" | "能启动界面"→"有演示"→"可分享" |
| **失败处理** | 阻塞后无期限等待 | 1天内必须解决或取消 |
| **完成标准** | 完美通过所有测试 | 80%可用就整合，下个Wave再优化 |

## 三、详细工作流程

### 3.1 Wave规划阶段

**参与者**: Lead + Planner  
**时长**: 1-2天  
**输出**: Wave目标文档 + 任务包

```yaml
Planner的职责:
  1. 评估当前真实状态
     - 哪些功能"可用"（虽然不完美）
     - 哪些功能"严重阻塞"
     - 哪些功能"接近完成"
  
  2. 定义Wave目标
     - 必须是一句话能说清的目标
     - 必须可以在规定时间内完成
     - 必须有明确的验收标准
  
  3. 生成任务包（1-2个）
     - 明确前置依赖（必须先完成什么）
     - 识别循环依赖（发现就拒绝）
     - 评估工作量（小/中/大）
     - 并行边界说明（哪些文件会改）
     - 回滚方案（失败怎么办）

Lead的职责:
  - 审核Planner的方案
  - 确认目标是否清晰
  - 批准任务包派发
  - 决定并行度（通常1-2个包）
```

**示例：Wave 1规划**

```yaml
Wave 1: 修复构建阻塞
目标: 能本地启动Workbench看到界面
时长: 1周
包数: 2个

包1: WAVE1-WEB-BUILD
  owner: worker-c
  objective: 修复Web TypeScript构建
  effort: 小（1-2天）
  dependencies: 无
  paths: apps/web/**, packages/dgos-ui/**
  acceptance: pnpm build成功，apps/web/dist存在

包2: WAVE1-WORKBENCH-LAUNCH  
  owner: worker-d
  objective: Tauri能打包并启动窗口
  effort: 中（2-3天）
  dependencies: 包1（需要web dist）
  paths: apps/desktop/**
  acceptance: 本地启动，看到界面（功能可以不完整）

并行度: 串行（包2依赖包1）
风险: Web构建可能有深层问题，预留1天buffer
```

### 3.2 任务执行阶段

**参与者**: Worker + Verify  
**时长**: 根据任务包估算  
**关键**: 快速反馈循环

```
快速反馈循环（新增）:

Worker完成任务
    ↓ (立即)
Worker自检（运行基本测试）
    ↓ (提交报告)
Verify快速预检（目标30分钟内）
    ├→ PASS: 标记ready_for_integration
    └→ FAIL: 立即返回Worker修复
              ↓
         Worker修复（目标1天内）
              ↓
         Verify复检
```

**Worker的工作方式**：

```yaml
接到任务后:
  1. 读取任务包（路径、目标、验收标准）
  2. 读取相关文档和代码
  3. 创建独立worktree（如果是代码任务）
  4. 只改allowed_paths中的文件
  5. 配套写测试
  6. 运行验证命令
  7. 提交标准报告

报告格式:
  status: completed | partial | blocked
  work_package: WAVE1-WEB-BUILD
  files_changed: [...]
  tests_added: [...]
  commands_run:
    - command: pnpm build
      result: passed
      evidence: dist目录生成，大小5.2MB
  implementation_facts: [...]
  open_risks: [...]
  
阻塞处理:
  - 遇到技术阻塞：立即报告Lead，不空耗时间
  - 遇到决策阻塞：列出选项，让Lead决定
  - 超过预估工作量：通知Lead调整计划
```

**Verify的工作方式**：

```yaml
预检（Worker完成后立即执行）:
  1. 检查任务包边界（是否改了不该改的文件）
  2. 运行基本检查（构建、基础测试）
  3. 30分钟内给出结论
  
  结论:
    - PASS: ready_for_integration（可以整合）
    - FAIL: 返回Worker，说明问题和证据
  
  优先级:
    P0 (立即): 构建失败、测试crash、路径越界
    P1 (1小时): 测试失败、文档不一致
    P2 (当天): 代码风格、优化建议

完整检查（Lead决定整合后）:
  - 运行适用的门禁检查
  - 检查文档一致性
  - 生成证据报告
```

### 3.3 整合阶段

**参与者**: Lead  
**时机**: 不等所有包完成，可以滚动整合

```yaml
Lead的整合策略:

旧模式: 等7个包全部完成 → 一次性整合 → 发现冲突 → 返工
新模式: 1个包ready → 立即整合 → 下个包基于新baseline

整合时机:
  - 包通过Verify预检
  - 没有明显冲突
  - 80%可用（不要求完美）
  
整合流程:
  1. 检查Verify的预检报告
  2. 如果PASS且无明显问题，决定整合
  3. Worker合并到main（或staging分支）
  4. 更新delivery-board状态
  5. 通知其他Worker新的baseline
  
优先整合over完美:
  - 有些小问题可以下个Wave修
  - 不要追求100%完美
  - 保持节奏比完美更重要
```

### 3.4 阻塞处理

**关键原则**: 不让包阻塞超过1天

```yaml
Lead每天检查清单:
  - 每个包的实际状态（不只看herdr idle/done）
  - 是否有超过24小时没进展的包
  - 是否有循环等待的依赖
  - Worker是否遇到无法解决的阻塞

阻塞处理决策树:

包阻塞超过1天
    ↓
Lead介入分析
    ├→ 技术问题: 
    │   ├→ 能快速解决 → 派发给其他Worker协助
    │   └→ 需要重新设计 → 取消包，返回规划
    │
    ├→ 依赖阻塞:
    │   ├→ 依赖包接近完成 → 继续等，但设deadline
    │   └→ 依赖包遥遥无期 → 调整依赖或取消包
    │
    └→ 决策阻塞:
        ├→ 有明确选项 → Lead当天决定
        └→ 需要用户决策 → 向用户请求，暂停包

取消包的标准:
  - 3天内无法完成
  - 阻塞其他包的关键路径
  - 技术方案有根本性问题
  
取消后:
  - 保留代码到独立分支
  - 更新任务包状态为cancelled
  - Planner重新规划替代方案
```

## 四、角色职责矩阵

### 4.1 Lead（我）

```yaml
核心职责: 全局协调、快速决策、每天检查

每天工作:
  早上:
    - 检查所有包的实际进展
    - 识别阻塞和风险
    - 决定今天的优先级
  
  全天:
    - 快速响应阻塞（目标2小时内）
    - 做简单决策（不升级给用户）
    - 协调依赖和冲突
  
  晚上:
    - 更新delivery-board
    - 写Lead日志
    - 规划明天的工作

权限:
  可以做:
    - 批准任务包
    - 决定整合时机
    - 取消阻塞的包
    - 调整任务优先级
    - 在授权范围内做技术决策
  
  不能做:
    - 改变版本范围（需要用户）
    - 修改核心业务规则（需要用户）
    - 直接写产品实现（派发Worker）
    - 默默用代码覆盖需求

承诺:
  - 每天至少检查一次
  - 阻塞1天内解决
  - 简单决策2小时内
  - 每个Wave结束总结
```

### 4.2 Planner

```yaml
核心职责: 规格、任务拆分、依赖分析

每个Wave开始前:
  - 评估真实状态
  - 定义Wave目标
  - 生成任务包（带依赖分析）
  - 做Ready检查

任务包质量要求:
  必须包含:
    - 依赖分析（前置、循环）
    - 并行边界（文件、API）
    - 工作量评估（小/中/大）
    - 回滚方案
  
  禁止:
    - 生成超过5个并行包
    - 创建循环依赖
    - 没有明确验收标准

Wave执行中:
  - 响应任务包修订需求
  - 记录文档变更
  - 准备下个Wave规划
```

### 4.3 Worker-A/B/C/D

```yaml
核心职责: 执行任务包，快速交付

工作方式:
  - 只做任务包范围内的工作
  - 代码配套测试
  - 遇阻立即报告
  - 完成后标准报告

独立worktree:
  - 代码任务默认用独立worktree
  - 路径: .herdr/worktrees/WAVE1-WEB-BUILD/
  - 完成后由Lead决定合并
  
领域划分:
  - Worker-A: 平台、核心服务、数据
  - Worker-B: Provider、AI、安全
  - Worker-C: Web、UI、浏览器
  - Worker-D: Native、Tauri、运行时
  
注意: 领域只是默认路由，任务包优先
```

### 4.4 Worker-E（新明确）

```yaml
核心职责: 构建、打包、CI/CD、发布工具

明确负责的代码路径:
  - apps/desktop/scripts/*     (构建脚本)
  - scripts/v1-candidate*.mjs  (候选构建)
  - scripts/build-*.mjs        (构建工具)
  - deployment/**              (部署配置)
  - .herdr/candidates/**       (候选记录)

典型任务:
  - 修复构建脚本
  - 生成候选manifest
  - 配置CI/CD
  - 打包发布工具
  - 收集证据

明确不做:
  - 整合其他Worker的业务代码（Lead做）
  - 修复业务逻辑bug（回派原owner）
  - 覆盖其他Worker的实现路径
```

### 4.5 Verify

```yaml
核心职责: 快速反馈、证据检查

新工作方式:
  预检模式（快速）:
    - Worker完成后立即执行
    - 目标30分钟内响应
    - 只检查基本问题
    - 给出PASS/FAIL结论
  
  完整检查（整合后）:
    - Lead决定整合后执行
    - 运行完整门禁
    - 生成证据报告

不再等待"所有Writer停止":
  - 旧规则：所有Writer停止 → Verify才能开始
  - 新规则：每个Worker完成 → 立即Verify预检
  
超时监控:
  - 发现Worker包超过1天没进展
  - 主动通知Lead
  - 建议: 继续等/返工/取消
```

## 五、V1-MVP策略

### 5.1 什么是MVP

```yaml
MVP (Minimum Viable Product):
  不是: 功能残缺的半成品
  而是: 能演示核心价值的最小闭环

V1-MVP目标:
  核心用户故事:
    "管理员启动DGOS Workbench，配置一个AI Provider，
     执行一个Task看到结果，安装并调用一个Skill"
  
  演示形式:
    - 5-8张真实截图
    - 3-5分钟演示视频
    - 可复现的安装步骤
    - 标注"Tech Preview"
  
  质量标准:
    - 单机macOS环境
    - 核心路径能跑通
    - 有基本错误处理
    - 不要求生产级性能/安全
```

### 5.2 明确不做的事

```yaml
V1-MVP明确不做:
  
  功能范围:
    ❌ 所有12个FR的完整验收
    ❌ 所有负面用例测试
    ❌ 完整的权限矩阵测试
    ❌ 所有边界条件处理
    ✅ 3-5个核心FR的基本路径
  
  质量标准:
    ❌ 生产级镜像安全扫描
    ❌ 多环境部署验证
    ❌ 性能压测
    ❌ 灾备恢复测试
    ✅ 本地环境基本可用
  
  测试覆盖:
    ❌ 202个测试全部通过
    ❌ 所有E2E场景
    ❌ 跨平台测试（Linux/Windows）
    ✅ 核心路径的smoke test
  
  交付物:
    ❌ 生产级发布包
    ❌ 完整文档
    ❌ 运维手册
    ✅ 演示视频和Tech Preview包
```

### 5.3 从MVP到正式版的路径

```yaml
迭代路径:

V1-MVP (Tech Preview)
    ↓
V1.0 (正式版)
    - 补全所有12个FR
    - 通过完整E2E
    - 生产级质量
    ↓
V1.1, V1.2... (持续改进)

重点: 
  - MVP是为了验证可行性
  - 不是降低标准
  - 而是分阶段交付
```

## 六、实战案例：Wave 1执行

### 案例：修复Web构建阻塞

**背景**: Web TypeScript构建失败，阻塞Workbench打包

#### 旧模式会怎么做（失败案例）

```
Day 1: 创建GAP-WEB-BUILD-01包，派发Worker-C
Day 2: Worker-C修复了3个错误，还有2个
Day 3: Worker-C继续修，发现是tsconfig问题
Day 4: Worker-C修改tsconfig，但不确定对其他包的影响
Day 5: Worker-C等Planner确认tsconfig改动
Day 6: Planner说需要检查所有包
Day 7: 发现改动影响了另一个GAP包
Day 8: 创建新的GAP-TSCONFIG包
Day 9: 两个包互相依赖，都blocked
Day 10+: 陷入僵局...
```

#### 新模式会怎么做（成功案例）

```yaml
Day 1 上午:
  Lead: 派发WAVE1-WEB-BUILD给Worker-C
  Worker-C: 读取任务包，创建独立worktree
  Worker-C: 开始修复TypeScript错误

Day 1 下午:
  Worker-C: 修复了3个错误，发现tsconfig问题
  Worker-C: 立即报告Lead："需要改tsconfig，可能影响其他包"
  Lead: 快速决策："改吧，影响其他包的话我们统一处理"
  Worker-C: 修改tsconfig，继续修复

Day 2 上午:
  Worker-C: 完成修复，pnpm build通过
  Worker-C: 提交报告（包含dist大小、构建时间）
  Verify: 30分钟内预检
    - 检查构建确实通过 ✓
    - 检查dist目录存在 ✓
    - 检查基本页面能加载 ✓
    - 结论: PASS, ready_for_integration

Day 2 下午:
  Lead: 检查报告，决定整合
  Worker-C: 合并到main
  Lead: 更新baseline
  Lead: 通知Worker-D："Web构建已修复，可以开始WAVE1-WORKBENCH-LAUNCH"

Day 3+:
  Worker-D: 基于新的web dist开始打包Workbench
  如果发现tsconfig问题: 立即报告，当天解决
```

#### 对比总结

| 维度 | 旧模式 | 新模式 |
|------|--------|--------|
| **决策速度** | 5天（等Planner检查所有包） | 2小时（Lead快速决定） |
| **问题发现** | Day 7（整合时） | Day 1（立即报告） |
| **完成时间** | 10+天（陷入僵局） | 2天（快速交付） |
| **阻塞处理** | 创建新包，加重负担 | Lead当天解决 |
| **反馈周期** | 无限长（等所有完成） | 30分钟（立即Verify） |

## 七、成功指标

### 7.1 流程指标

```yaml
每个Wave:
  - 包数: ≤3个
  - 完成时间: 按计划±2天
  - 阻塞时间: 每个包<1天
  - Verify响应: <30分钟
  - Lead决策: <2小时

整体进度:
  - Wave 1: 1周内完成
  - Wave 2: 2周内完成
  - Wave 3: 1周内完成
  - 总计: 4周完成V1-MVP
```

### 7.2 质量指标

```yaml
V1-MVP验收:
  核心路径:
    - Workbench能启动 ✓
    - Provider能配置 ✓
    - Task能执行并看到结果 ✓
    - Skill能安装和调用 ✓
  
  交付物:
    - 演示视频 3-5分钟 ✓
    - 截图 5-8张 ✓
    - 安装包 macOS ✓
    - Tech Preview标注 ✓
  
  不要求:
    - 所有测试通过 ✗
    - 生产级性能 ✗
    - 完整错误处理 ✗
```

### 7.3 团队健康指标

```yaml
健康的团队:
  - Worker没有超过1天的阻塞
  - Verify能快速响应
  - Lead每天都在检查
  - 每周都有可见进展
  - 没有互相推诿

不健康的信号:
  - 包长期blocked
  - Worker等待无期限
  - Lead不做决策
  - 问题堆积不处理
  - 回到旧模式（7个包同时进行）
```

## 八、常见问题

### Q1: Wave内的包失败了怎么办？

```yaml
A: 快速止损，不要拖延

Day 1: Worker报告无法完成
    ↓
Day 1: Lead分析原因
    ├→ 技术可解决 → 延长1-2天 or 换Worker
    ├→ 方案有问题 → 取消包，Planner重新规划
    └→ 依赖阻塞 → 调整Wave顺序

重点: 不要让失败的包拖累整个Wave
```

### Q2: Worker完成但Verify说不通过？

```yaml
A: 快速反馈，立即修复

Verify预检FAIL
    ↓
30分钟内给出具体问题
    ↓
Worker当天修复
    ↓
Verify复检

如果连续3次不通过:
  → Lead介入，可能是任务包定义有问题
```

### Q3: 发现需要改变版本范围怎么办？

```yaml
A: 暂停，向用户请求决策

Worker发现: "这个功能需要重新设计架构"
    ↓
Worker报告Lead
    ↓
Lead评估: 这是重大变更，超出当前授权
    ↓
Lead向用户请求决策
    ↓
暂停相关包，等待用户回复
```

### Q4: 80%可用的标准是什么？

```yaml
A: 核心路径通，已知问题可接受

80%可用:
  ✓ 正常路径能跑通
  ✓ 基本错误处理
  ✓ 已知问题已记录
  ✓ 不阻塞下游
  
  可接受的问题:
  - UI不够美观
  - 某些边界情况未处理
  - 性能不是最优
  - 日志不够完善

  不可接受的问题:
  - 核心路径不通
  - 数据会丢失
  - 严重安全问题
  - 阻塞其他包
```

### Q5: 什么时候恢复旧模式？

```yaml
A: 永远不要

旧模式的问题是结构性的，不是执行问题
  - 7个包同时进行 → 永远不会比3个包快
  - 等所有完成才验证 → 永远会堆积问题
  - 追求完美 → 永远无法交付

如果新模式不work:
  - 不是恢复旧模式
  - 而是调整Wave定义、包的粒度、并行度
  - 核心原则不变: 小步快跑、快速反馈、优先整合
```

## 十、附录：术语对照

```yaml
术语对照表:

Wave:
  - 一个时间盒（1-2周）
  - 有唯一明确的目标
  - 包含1-3个任务包
  - 独立验收

任务包 (Task Package):
  - 一个可独立完成的工作单元
  - 有明确的owner
  - 有estimated effort
  - 有acceptance criteria

快速反馈循环:
  - Worker完成 → Verify预检 → 快速修复
  - 目标30分钟响应
  - 不等其他包完成

预检 vs 完整检查:
  - 预检: Worker完成后立即执行，基本检查
  - 完整检查: Lead整合后执行，所有门禁

80%可用:
  - 核心路径通，已知问题可接受
  - 优先整合，下个Wave再优化

阻塞1天原则:
  - 任何包阻塞超过1天必须处理
  - Lead当天解决或取消

V1-MVP:
  - Tech Preview级别的最小演示
  - 不是完整的V1正式版
  - 验证可行性，快速迭代
```
