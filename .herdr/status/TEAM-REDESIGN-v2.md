# DGOS 高效Agent团队设计方案 v2.0

**设计者**: Lead  
**日期**: 2026-10-03  
**原则**: 简洁、高效、专注产出、最小化中间文档

---

## 一、核心设计理念

### 1.1 问题诊断

**旧团队的根本问题**：
```
❌ 角色过多：Lead + Planner + 5个Worker + Verify = 8个角色
❌ 文档爆炸：.herdr/下425个MD文件，大量重复和矛盾
❌ 流程僵化：每个任务都要生成context-pack、task-pack、report
❌ 职责不清：Planner写文档，Worker写代码，Lead协调，实际上互相推诿
❌ 中间文档泛滥：各种GAP-*、CONTEXT-PACK，没人读，只是流程产物
```

**本质问题**：
- **过度流程化**：为了管理而管理，不是为了产出
- **文档不是目的**：权威文档在`docs/`，`.herdr/`应该极简
- **角色太多导致协调成本高**：8个角色，7个在等Lead派发

### 1.2 新设计原则

```yaml
1. 最小化团队：3个核心角色足够
2. 产出导向：只写必需文档，直接改代码
3. 权威唯一：docs/是唯一真相，.herdr/只记录执行状态
4. 快速迭代：小步快跑，当天看到成果
5. 自治优先：减少Lead介入，Agent自主推进
```

## 二、新团队结构

### 2.1 团队配置

```
精简为3个核心角色：

┌──────────────────────────────────────┐
│          用户 (你)                    │
└──────────────────────────────────────┘
              ↓
┌──────────────────────────────────────┐
│   Lead (我) - 战略协调者              │
│   - 定义目标和优先级                  │
│   - 解决阻塞和冲突                    │
│   - 每天检查1次，不是每小时           │
└──────────────────────────────────────┘
              ↓
    ┌─────────┴─────────┐
    ↓                   ↓
┌─────────┐      ┌──────────┐
│ Builder │      │  Checker │
│ 建设者   │      │  检查者   │
└─────────┘      └──────────┘

Builder (2个并行实例):
  - Builder-A: 后端、数据、API
  - Builder-B: 前端、Native、构建

Checker (1个实例):
  - 验证、测试、证据收集
```

### 2.2 为什么3个角色就够？

**对比旧团队**：

| 旧角色 | 是否必需 | 新方案 |
|--------|----------|--------|
| Lead | ✅ 必需 | 保留，但减少介入频率 |
| Planner | ❌ 冗余 | 取消，Lead直接定义任务 |
| Worker-A/B/C/D/E | ❌ 过多 | 合并为2个Builder |
| Verify | ✅ 必需 | 保留，改名Checker |

**理由**：
- **Planner冗余**：生成context-pack、task-pack只是流程，不创造价值
  - Lead直接从docs/读取权威规格，定义任务
  - 不需要中间"任务包"文档，直接给Builder明确指令
  
- **5个Worker过多**：
  - 领域划分（平台/Provider/Web/Native/集成）只是标签
  - 实际任务经常跨领域，反而增加协调成本
  - 2个Builder并行足够，每个Builder都是全栈能力
  
- **2个Builder的好处**：
  - 可以并行2个独立任务
  - 减少依赖冲突（只有2个，容易协调）
  - Builder之间平等，没有"Worker-E不能改Worker-A代码"的矛盾

## 三、角色详细定义

### 3.1 Lead（我）- 战略协调者

```yaml
核心职责:
  - 从docs/理解V1目标和当前状态
  - 定义每周的2-3个关键任务
  - 派发给Builder
  - 解决阻塞和技术决策
  - 每天检查1次（不是每小时）

工作方式:
  每周一:
    - 读取docs/当前版本文档
    - 读取V1-实现状态.md
    - 定义本周目标（1句话）
    - 拆分为2-3个独立任务
    - 派发给Builder-A和Builder-B
  
  每天晚上:
    - 检查Builder进展
    - 如果阻塞，当天解决
    - 如果顺利，不介入
  
  周五:
    - 总结本周成果
    - 规划下周任务

产出:
  - 每周目标（1页）
  - 每日检查日志（3-5行）
  - 周总结（1页）
  
不做:
  - 不写context-pack、task-pack
  - 不每小时检查
  - 不过度协调（Builder自主解决问题）
```

### 3.2 Builder - 建设者

```yaml
核心职责:
  - 全栈交付：代码 + 测试 + 基本文档
  - 自主解决技术问题
  - 遇到重大阻塞才报告Lead

能力要求:
  - 能读docs/权威规格
  - 能写后端、前端、数据库、测试
  - 能判断"这个改动是否需要Lead批准"
  
工作方式:
  接到任务:
    1. 读取docs/相关功能规格
    2. 读取当前代码
    3. 做计划（内部，不输出文档）
    4. 实施：代码 + 测试
    5. 自检：本地运行
    6. 提交：代码 + 运行证据
  
  遇到阻塞:
    - 技术问题：先尝试2小时，解决不了报告Lead
    - 决策问题：立即报告Lead（如"需要改架构"）
  
产出:
  - 代码（committed）
  - 运行证据（截图/日志/测试输出）
  - 简短说明（5-10行，不是长篇报告）
  
不做:
  - 不写长篇work-package报告
  - 不生成中间文档
  - 不等Lead批准每一步
```

**Builder-A vs Builder-B的划分**：

```yaml
Builder-A (后端为主):
  擅长: API、数据库、Worker、后端逻辑
  也能做: 前端改动（如果任务需要）
  
Builder-B (前端为主):
  擅长: React、UI、Tauri、构建打包
  也能做: 后端改动（如果任务需要）

重点: 这不是严格边界，而是默认分配
      如果Builder-A空闲，也可以做前端任务
```

### 3.3 Checker - 检查者

```yaml
核心职责:
  - 验证Builder的成果
  - 运行测试和检查
  - 收集证据
  - 快速反馈（2小时内）

工作方式:
  Builder提交后:
    1. 拉取代码
    2. 运行构建和测试
    3. 检查基本质量（不追求完美）
    4. 2小时内给结论：✅ PASS 或 ❌ FAIL + 具体问题
  
  PASS标准:
    ✅ 构建成功
    ✅ 相关测试通过（不要求全部）
    ✅ 核心功能可用
    ✅ 没有明显破坏
  
  FAIL标准:
    ❌ 构建失败
    ❌ 核心功能不work
    ❌ 测试大面积失败
  
产出:
  - ✅ PASS: 一行结论 + 测试输出截图
  - ❌ FAIL: 3-5行问题描述 + 错误日志
  
不做:
  - 不写长篇验证报告
  - 不追求100%测试覆盖
  - 不在Builder工作时预检（等Builder完成）
```

## 四、工作流程

### 4.1 周循环

```
周一上午 (Lead):
  1. 读取docs/V1-实现状态.md
  2. 定义本周目标（1句话）
  3. 拆分为2-3个任务
  4. 派发给Builder

周一下午 - 周五下午 (Builder + Checker):
  Builder工作 → 提交 → Checker验证 → PASS/FAIL
  如果FAIL → Builder当天修复 → 再验证
  如果PASS → 合并到main

周五晚上 (Lead):
  1. 总结本周成果
  2. 规划下周任务
  3. 向用户汇报
```

### 4.2 任务流转

```
Lead定义任务
    ↓
Builder接任务
    ↓
Builder工作（自主，不汇报过程）
    ↓
Builder提交代码 + 证据
    ↓
Checker验证（2小时内）
    ├→ ✅ PASS: 合并main
    └→ ❌ FAIL: Builder当天修复

阻塞处理:
  Builder遇阻 → 报告Lead → Lead当天解决
```

### 4.3 文档策略

```yaml
权威文档 (docs/):
  - 只读，不修改（除非用户要求）
  - V1-版本总览.md: 版本范围
  - V1-实现状态.md: 当前进度
  - 功能规格/**: 功能详细定义

执行记录 (.herdr/):
  - 极简，只记录必需信息
  - status.yaml: 当前任务和状态
  - weekly/: 每周总结（1页/周）
  - evidence/: 运行证据（截图、日志）
  
  不要:
    ❌ context-pack
    ❌ task-pack
    ❌ 长篇报告
    ❌ 中间文档

代码即文档:
  - commit message要清晰
  - PR description说明改动
  - 代码注释说明复杂逻辑
```
