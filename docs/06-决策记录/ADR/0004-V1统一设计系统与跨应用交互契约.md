# ADR-0004 V1 统一设计系统与跨应用交互契约

- 状态：Accepted
- 日期：2026-09-27
- 决策人角色：产品与技术负责人
- 关联需求/决策：D025、D028、GC-06–GC-10、V1 界面与交互规范

## 背景

DGOS 是独立的应用操作系统，需要同时承载系统设置、应用目录、Provider、Skill、MCP、系统助手和不同领域的 APP。桌面端与 Web 端共用前端，但窗口、文件、钥匙串、通知和生命周期等宿主能力不同。DX OS 的截图和开发者资料证明了窗口、多窗口、设置分组、扩展管理和应用化入口对这类系统有参考价值，但它们不能直接成为 DGOS 的品牌、协议或实现契约。

如果每个 APP 自建颜色、窗口、权限提示、任务状态、错误处理和交互组件，用户会得到多个互不一致的产品，跨端维护成本也会随应用数量增加。反过来，如果平台限制所有领域内容，又无法承载无限画布、表格、媒体、天气或网盘等不同类型的应用。因此需要明确“平台统一什么、应用可以表达什么”，并把规则写入可复用的代码层和 manifest 校验层。

## 备选方案

### 方案 A：每个应用独立设计

- 优点：初期实现最快，应用可以自由选择组件和视觉风格。
- 缺点：窗口、主题、权限和异步状态会分叉；桌面/Web 行为难以保持一致；第三方应用无法获得稳定的系统能力；无障碍和安全脱敏容易遗漏。

### 方案 B：平台提供 Design Tokens、UI Kit、AppShell 和 Host Adapter，应用消费公开契约

- 优点：统一视觉和状态语义，桌面/Web 共用，系统级权限和任务可审计；应用仍可自定义领域布局和工具；未来 Windows 或其他宿主只需替换适配层。
- 缺点：V1 必须先建设组件、文档、主题、可访问性和 manifest 校验；平台需要维护兼容性和版本策略；过度约束会降低领域创新，需要明确扩展边界。

### 方案 C：直接复刻 DX OS 的界面和运行时

- 优点：可以快速获得接近参考软件的外观和部分交互。
- 缺点：引入不属于 DGOS 的品牌、协议、Bridge 和技术栈；不能解释 DGOS 自身的权限、Provider、任务和跨端边界；后续迁移代价高，无法作为独立系统的长期契约。

## 决策

选择方案 B。

1. `packages/design-tokens` 是颜色、字体、间距、尺寸、圆角、层级、动效、主题和国际化基础值的唯一来源。组件和应用不得散落原始值。
2. `packages/dgos-ui` 提供可访问的导航、操作、输入、数据、反馈、内容和布局组件。组件必须覆盖浅色/深色、键盘、ARIA、焦点、加载、禁用、错误和减少动态效果状态。
3. `packages/app-shell` 负责窗口、页签、Dock/启动器、导航、命令面板、通知、任务中心和全局错误边界。应用不能自建平行窗口管理或权限确认层。
4. `packages/host-adapter` 隔离 macOS Tauri、Web 和未来 Windows 的文件选择器、钥匙串、窗口、通知和生命周期差异。业务路由、任务状态、错误 ID 和 API 事件保持一致。
5. 应用负责领域路由、数据、表格、画布、媒体预览和专用工具。应用可以在 manifest 中声明 `accentColor`（仅引用允许的语义 token）、窗口偏好、路由、命令和领域 token，但不能覆盖系统主题、字体、窗口生命周期、权限策略或系统状态。
6. 所有安装、Provider 请求、Skill/MCP 连接、导出、外部调用和长任务都遵守统一状态：发起、进行中、成功、失败、取消或无权限，并显示稳定的 request/task ID 和恢复路径。
7. DX OS 的视觉、字段、协议和运行时只作为研究来源。DGOS 的初始视觉方向是中性底色、蓝色主强调色、有限材质和 4 px 间距系统；真实运行截图可以通过新的 ADR 调整 token，但不能改变平台/应用边界而不更新契约。

## 后果

### 正面后果

- V1 平台控制面和 DGOS AI 工作台能够先验证统一的窗口、主题、Provider、任务、权限和错误体验。
- 新的文件、天气、二维码、网盘、无限画布等 APP 可以复用平台能力，并把工程重点放在领域功能。
- Web、macOS 和未来 Windows 的差异有明确归属，不会污染应用业务代码。
- UI 验收可以用统一的 token、组件契约、可访问性扫描和双宿主 E2E 形成证据链。

### 成本和风险

- V1 前期需要建设 UI Kit 文档、主题测试、组件视觉回归和 manifest 校验，不能在应用页面完成后再补。
- Design Tokens 和组件 API 需要版本化；破坏性变更必须经过 ADR、迁移说明和应用兼容检查。
- 领域应用可能需要超出通用 UI Kit 的交互（例如画布端口或 3D 时间线），这些能力必须以领域组件扩展形式实现，并继续遵守 Shell、任务、权限和秘密契约。
- 初始 token 尚未经过真实 DGOS 运行截图验证，当前只能标记为设计基线，不能标记为视觉验收通过。

## 验证

1. 构建 `design-tokens` 和 `dgos-ui` 的浅色/深色组件样例，使用键盘、屏幕阅读器和 75%–175% 显示倍率检查焦点、截断、对比度和操作可达性。
2. 在 macOS Tauri 和 HTTPS Web 端打开同一 V1 路由，验证窗口/面板、路由、Provider 任务、SSE 断线恢复、错误 ID 和权限拒绝的业务语义一致。
3. 对 Provider、Skill、MCP 和系统助手执行提交、取消、失败、重试和无权限路径，保存任务事件、截图和 E2E 结果；不能用静态组件截图替代任务证据。
4. 对含非法主题覆盖、窗口生命周期覆盖或未声明权限的 manifest 运行校验，平台必须拒绝加载并给出字段级错误。
5. UI-AC-001–UI-AC-007 必须映射到组件视觉/可访问性测试、双宿主 E2E、manifest 校验和多语言/倍率截图；真实证据产生前，状态保持“待验证”。

## 重评条件

- 真实运行证明 UI Kit 无法满足某类领域交互时，新增领域扩展组件或 ADR，不允许应用绕过 Shell/权限/任务契约。
- Windows 或其他宿主无法通过现有 Host Adapter 提供等价能力时，先扩展 Host Adapter 契约，再考虑应用层差异。
- 组件包出现跨应用破坏性升级、主题 token 不足或无障碍门禁持续失败时，重新评估 token 版本和组件分层。
- 真实用户研究或 DGOS 截图证据表明初始视觉 token 降低可读性、密度或效率时，可通过新 ADR 调整具体值；平台/应用职责边界仍需单独决策。
