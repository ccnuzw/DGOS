# ADR-0003 V1 技术栈与可替换运行时

- 状态：Accepted
- 日期：2026-09-27
- 决策人角色：产品负责人 / 技术负责人
- 关联需求/决策：D018、D019、D026、D027；V1-FR-001、V1-FR-002、V1-FR-003、V1-FR-005、V1-FR-007、V1-FR-009

## 背景

DGOS 是独立运行的应用操作系统，需要在 V1 同时提供 macOS 桌面入口和可由 Docker Compose 部署的 HTTPS Web 入口。两个入口必须共享 React 前端、设计系统、路由语义和 DGOS API；V1 还必须承载真实 `openai-compatible` Provider、SSE 文本流式任务、官方 Skill/MCP 应用和受控扩展运行时。技术栈需要先支持平台纵向闭环，同时为 Windows、正式登录、多用户/组织、画布和第三方扩展保留边界。

## 备选方案

### 方案 A：Tauri 2 + TypeScript/Node（采用）

- 前端：React + TypeScript + Vite；pnpm workspace，共享 UI、SDK、应用运行时和契约包。
- 桌面：Tauri 2 + Rust Shell，负责窗口、菜单、Dock/托盘、文件选择器、系统钥匙串和本地服务生命周期。
- API：Node.js LTS + TypeScript + Fastify 模块化单体，提供版本化 HTTP API 和 SSE。
- Worker：独立 Node.js/TypeScript Worker，使用 Redis 适配器和可替换队列接口。
- 扩展：独立 `extension-runner`，通过受限 JSON-RPC/stdio 或本地 IPC 执行 Skill、MCP、Agent。
- 存储：PostgreSQL、S3 兼容对象存储（本地 MinIO）和 Redis。
- Web：反向代理 + API + Worker + PostgreSQL + Redis + MinIO 的 Compose 拓扑。

方案 A 的主要理由是前端、API、Worker、SDK 和 Provider 适配器可以共享 TypeScript 类型与错误语义，缩短 V1 的 Provider、流式任务和双入口反馈周期；Tauri 将原生权限留在 Rust 宿主并保持较小的桌面壳层。

### 方案 B：Electron + Go（保留备选）

方案 B 使用 React/TypeScript 前端、Electron 桌面、Go API/Worker、PostgreSQL、S3 和 Redis。它在静态二进制、常驻并发和 Electron 原生生态方面有优势，但引入 Go/TypeScript 跨语言契约、较大的桌面资源开销和更长的 Provider/扩展调试链。完整比较保留在 [V1 技术栈候选与专项讨论](../../04-技术架构/当前版本/V1-技术栈候选与专项讨论.md)。

## 决策

V1 采用方案 A 作为开发基线。所有业务语义以 HTTPS JSON、SSE、OpenAPI 3.1、JSON Schema 和 DGOS SDK 为准；Tauri command 只承载窗口、文件、钥匙串、系统菜单等宿主能力，不能形成第二套 Provider、AI Task 或权限 API。

核心运行边界如下：

1. API/Worker 采用模块化单体优先，Provider Adapter、秘密边界、任务执行和扩展执行保留独立进程/接口边界。
2. 首批协议为 `openai-compatible`，通过 `ProtocolAdapterRegistry` 和版本化 `ProviderCapabilityDescriptor` 扩展；前端不根据供应商名称猜测能力。
3. AI Task 使用统一状态、取消、幂等、错误映射和 SSE 事件语义；查询 API 是最终状态权威。
4. Skill/MCP/Agent 通过独立 `extension-runner` 执行，不能在浏览器页面或核心进程内直接读取秘密和其他应用私有状态。
5. PostgreSQL 是权威事务数据存储，S3/MinIO 承载二进制和 artifact，Redis 承载队列/缓存；应用通过领域接口访问数据。
6. `subjectType/subjectId`、权限、所有权和审计字段按未来多用户/组织模型设计；V1 不交付正式账号注册和组织协作。

## 可替换边界

未来可以在不改写 DGOS 产品契约的前提下，将 Node Worker 替换为 Go Worker，或按容量、故障隔离和发布频率将部分 API 领域迁移到 Go。替换必须继续兼容 React 前端、Tauri 宿主接口、SDK、OpenAPI/JSON Schema、Provider Adapter、Task/Event 和 extension-runner 协议。Go 不是 V1 必选运行时。

## 后果

- 正面：V1 以一套主语言贯通 Provider、SSE、SDK 和前端，降低平台基础闭环的早期协作成本；桌面与 Web 共用业务包；运行时和扩展仍有进程隔离。
- 代价：团队需要维护少量 Rust 宿主代码，并验证 Tauri 的 macOS 打包、签名、钥匙串、窗口和本地服务生命周期。
- 代价：Node Worker 和 extension-runner 必须明确 CPU、内存、网络出口、超时、重试和子进程配额。
- 运营：Web 必须提供可复现的 Compose 服务、持久卷和健康检查；桌面发行包需要处理本地 API/Worker 的启动、迁移、退出和任务恢复。
- 备选：方案 B 仅在重评条件满足时启用，不得在 V1 中并行维护两套核心领域实现。

## 验证要求

本 ADR 只接受技术设计基线，不宣称实现已验证。进入开发门禁后必须分别提供：

- macOS Tauri 窗口、文件选择器、钥匙串、签名/更新和本地服务生命周期证据；
- Docker Compose Web、API、Worker、PostgreSQL、Redis、MinIO 健康检查与数据卷证据；
- Web/桌面共享前端路由、Provider 配置、模型拉取、真实文本任务、SSE 断线恢复和最终查询一致性证据；
- `openai-compatible` adapter 的模型目录、能力 descriptor、超时/取消/错误映射和秘密不泄露 contract test；
- extension-runner 的权限、秘密句柄、资源配额、审计和故障隔离证据。

验证记录必须进入版本实现状态和测试/发布证据链；规划命令、静态检查或模拟 Provider 不得写成运行通过。

## 重评触发条件

满足以下任一条件时，新增 ADR 重评方案 B 或局部迁移：Node Worker 的实测资源上限无法满足已批准负载；Tauri 无法覆盖 macOS/Windows 宿主验收；Electron 原生能力成为硬性产品依赖；团队已有稳定的 Go 发布与跨语言契约能力且收益超过迁移成本；或容量、故障隔离、合规/数据驻留要求需要独立 Go 服务。重评必须保留公共契约并提供迁移、回滚和兼容证据。
