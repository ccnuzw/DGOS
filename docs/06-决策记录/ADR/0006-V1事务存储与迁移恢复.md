# ADR-0006 V1 事务存储、迁移与恢复

- 状态：Accepted
- 日期：2026-10-01
- 决策人角色：技术负责人、数据负责人、发布负责人
- 关联需求/决策：`D027`、`D034`、`D035`、`V1-FR-001`、`V1-FR-010`–`V1-FR-015`
- 前置决策：[ADR-0003](0003-V1技术栈与可替换运行时.md)、[ADR-0005](0005-V1身份秘密Provider治理与用量机器契约.md)

## 背景

V1 已接受 PostgreSQL 作为权威事务数据存储，S3/MinIO 作为对象存储，Redis 作为队列和缓存。但身份、Provider 账号、审计、额度和任务之间的状态约束仍只存在于逻辑模型中。若不冻结事务边界、迁移兼容规则和恢复语义，唯一性、幂等、撤销传播、额度预留和审计完整性会依赖应用代码的偶然行为。

本文冻结工程设计基线，不表示已有物理表、migration、备份或恢复演练证据。

## 决策

### 1. 存储职责

1. PostgreSQL 是 `AdminPrincipal`、`AdminSession`、`ApiKeyRecord`、`ProviderAccount`、`ProviderBinding`、`ConnectionTest`、`AuditEvent`、`RetentionJob`、`UsageEvent`、`QuotaReservation` 及其版本化策略的权威存储。
2. S3/MinIO 只保存安装包、Artifact 和其他二进制对象；业务数据库只保存稳定对象引用、摘要、大小、媒体类型和完整性摘要。
3. Redis 只保存队列、租约、短期缓存和限流状态；Redis 数据丢失不得导致权限、审计、额度或任务终态丢失。
4. 领域服务只能通过 repository/domain interface 访问 PostgreSQL；Provider Adapter、前端和扩展 Runner 不直接访问数据库。

### 2. 事务与隔离

| 场景 | 数据库事务边界 | 并发保护 | 外部步骤 |
| --- | --- | --- | --- |
| 管理员引导/登录 | 主体、会话、脱敏认证结果和 audit outbox 同一事务 | 部署级初始化锁；主体唯一约束 | 认证 Secret 校验在事务外，成功结果必须幂等落库 |
| Session 续期/撤销 | 目标会话条件更新和审计 outbox 同一事务 | `sessionVersion` + 状态条件；撤销优先 | 不依赖缓存提交授权 |
| API Key 轮换 | 新 Key 摘要、rotation 状态和审计同一事务 | `rotationGroup` 条件更新 | 明文只在 Secret 写入成功后返回一次 |
| Provider 账号绑定/默认切换 | 账号、绑定、默认唯一状态和审计同一事务 | `version` 条件；默认值唯一约束 | Secret 写入/删除采用可重试补偿 |
| 连接测试 | queued 记录和审计先提交；终态独立条件更新 | 测试租约、终态条件更新 | 外部探测不可与数据库事务共享，超时由 worker 收敛 |
| Audit 高风险写入 | 业务状态和 outbox 同一事务 | `eventId` 唯一 | outbox publisher 异步投递 |
| Quota reservation | reservation、额度窗口计数和审计同一事务 | 行锁或等价原子条件更新 | Provider 调用在提交后进行 |
| Usage settle | usage 去重记录、reservation 终态和汇总同一事务 | `taskId+attemptId` 唯一 | 缺失 usage 进入 reconciliation，不猜测金额 |

默认事务隔离级别为 PostgreSQL `READ COMMITTED`。涉及额度、默认 Provider 或需要检查后写入的事务必须使用条件更新或目标行锁；不得把普通读取与后续写入之间的时间窗口当作并发保护。只有发现 `READ COMMITTED` 无法维持已冻结不变量时，才通过新增 ADR 局部提高隔离级别。

### 3. 物理约束基线

实际表名可按实现规范命名，但 migration 必须提供等价约束：

- 所有实体主键、外部稳定 ID 和 `requestId` 使用不可变标识；时间统一使用 UTC。
- `AdminSession`、`ApiKeyRecord`、`ProviderAccount`、`ProviderBinding`、`ConnectionTest`、`AuditEvent`、`RetentionJob`、`QuotaReservation` 和 `UsageEvent` 的稳定 ID 唯一。
- 需要幂等的写入建立作用域化唯一键：`requestId + operation scope`；Usage 使用 `taskId + attemptId`。
- Provider 默认账号、治理策略和额度策略的唯一性必须按 `subjectType + subjectId + protocol/metric/window` 作用域表达，不能由展示名保证。
- 状态迁移使用版本条件或显式状态条件；旧版本更新影响 0 行时返回 `version_conflict`，不得静默覆盖。
- 审计和用量明细只追加；更新只能写入状态收敛字段或派生汇总，不得原地改写业务事实。
- Secret 明文、密码、Cookie、Token、Authorization 和完整上游响应不得进入 PostgreSQL 业务表。
- 外键和删除策略必须避免级联删除 Task、Artifact、Audit、Usage 或仍被引用的 SecretRef；业务删除采用 revoked/hidden/removed 和受保护清理。

### 4. Migration 规则

1. migration 只向前兼容地增加表、列、索引或可回填字段；应用先兼容旧/新结构，再切换写入，最后才清理旧结构。
2. 每个 migration 必须具备稳定版本、checksum、明确的前置版本、锁定策略、预计耗时和回滚/停止说明。
3. 破坏性变更拆成 expand、backfill、switch、contract 四阶段；禁止在一次发布中直接删除仍被上一版本读取的列或索引。
4. backfill 必须分批、可暂停、可重入，并记录 checkpoint；失败只保留已提交批次，不回滚整个生产库。
5. migration 失败时停止发布，保留数据库和应用版本的兼容窗口；不得以手工 SQL 代替缺少登记的 migration。
6. 每次发布记录 migration 起止版本、文件 checksum、执行耗时、受影响行数、锁等待、前后关键计数和验证结果。

### 5. 恢复与清理

- 审计 outbox、RetentionJob 和 Quota reconciliation 都必须可从 checkpoint 重启，重复执行依靠唯一键或幂等状态安全跳过。
- Redis 重启后由 PostgreSQL 恢复待处理任务、租约过期项和待对账项；不能从 Redis 恢复业务真相。
- RetentionJob 删除前重新检查引用、状态和保留例外；失败记录原因并重试，不绕过保护条件。
- 备份必须同时覆盖 PostgreSQL、对象存储引用所需的元数据和密钥根配置；恢复后先进入只读校验，再开放写入。
- 额度 reconciliation 发现预留缺少结算时只进入明确的 `released`、`settled` 或 `needs_review` 终态，不自动猜测用量。

## 不采用的方案

### 方案 A：仅依赖应用代码约束

不采用。多 worker、多入口和崩溃恢复时无法保证唯一性、幂等和并发边界。

### 方案 B：所有状态写入串行队列

不采用。可以降低部分并发复杂度，但会把查询、认证和额度写入绑定到单一吞吐瓶颈，且不能替代数据库恢复和唯一约束。

### 方案 C：V1 直接使用 PostgreSQL 强串行化

不采用为默认方案。它会放大锁冲突和重试成本；V1 先用 `READ COMMITTED` 加显式条件更新/目标行锁，以实际并发测试结果决定是否局部升级。

## 后果

- 逻辑模型可以直接转化为可验证的 PostgreSQL migration、repository 和并发测试。
- 外部 Provider、Secret、对象存储和 Redis 故障不会被伪装成数据库事务成功。
- migration、备份恢复、outbox、清理和 reconciliation 成为发布门禁输入，而不是部署后的隐含运维工作。
- 仍需由实现阶段选择 migration 工具、具体表名、索引名、备份产品和锁超时参数；这些实现选择不得改变本文不变量。

## 验证要求

实现阶段必须提供：

1. 空库初始化、升级、重复执行和中途失败恢复测试。
2. 唯一键、版本冲突、默认账号唯一、`taskId+attemptId` 去重和引用保护测试。
3. 两个并发 reservation、session revoke/renew、Provider default 切换和 governance policy 更新测试。
4. outbox 重复投递、RetentionJob checkpoint 重启、Redis 丢失和 quota reconciliation 测试。
5. macOS 本地模式与 Docker Compose Web 模式的 migration 前后快照、checksum、耗时和回滚/停止证据。

当前没有产品源码、migration、运行环境、备份或上述测试证据；本 ADR 只冻结设计基线。
