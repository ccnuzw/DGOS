# ADR-0002 V1 共用前端与桌面宿主

- 状态：Superseded by ADR-0003（保留历史候选与共用前端边界论证）
- 日期：2026-09-26
- 决策人角色：待技术栈评审
- 关联需求/决策：D018、V1-FR-001、V1-FR-002、V1-FR-005、V1-FR-007

## 背景

DGOS 必须同时支持桌面端和 HTTPS Web。桌面端需要苹果风格窗口、Dock/启动台、系统菜单和本地能力；Web 端需要通过浏览器访问同一产品。若为两个入口分别实现应用业务，会造成路由、权限、任务状态和设计系统分叉。另一方面，桌面宿主需要访问钥匙串、窗口和文件选择器，不能把这些能力直接暴露给前端页面。

## 备选方案

| 方案 | 核心思路 | 优点 | 风险 | 适用条件 |
| --- | --- | --- | --- | --- |
| A | React/TypeScript 共享前端 + Tauri 2 Rust 宿主；Web 使用 HTTPS API，桌面使用同一 API 语义 | 业务复用高；宿主能力边界清楚；包体较小 | Rust 宿主需要维护；部分原生能力需跨平台适配 | 桌面体验重要且需要系统能力 |
| B | React/TypeScript 共享前端 + Electron 宿主 | Node 原生模块和桌面生态成熟；团队上手快 | 包体和资源占用较高；主进程权限边界更复杂 | 需要大量 Electron 专属生态或原生模块 |
| C | Web/PWA 为主，桌面只提供浏览器封装 | 实现最少；入口共享最高 | 窗口、钥匙串、安装生命周期和系统集成不足 | 只需要轻量 Web 工具，不适合 DGOS 的系统壳层目标 |

## 决策

暂定采用方案 A 作为 V1 原型和技术验证基线：React + TypeScript 前端包由 Web 和 Tauri 桌面宿主共同消费；V1 桌面发行目标为 macOS，Windows 作为后续目标平台。桌面宿主只承载窗口、菜单、Dock/托盘、文件选择器、系统钥匙串和本地服务生命周期，这些能力必须通过可替换的平台适配接口提供。Web V1 提供 Docker Compose 本地部署形态。业务操作全部通过版本化 DGOS API/SDK，Tauri command 不得形成第二套领域契约。

本 ADR 的共用前端和宿主边界已由 ADR-0003 的完整技术栈决策继承；其中关于“待最终接受”的历史措辞不再作为当前门禁依据。运行验证仍按 ADR-0003 的验证要求执行。

## 后果

- 正面：应用业务、权限调用、Provider 任务和设计系统可以共享；桌面/Web 的差异集中在宿主适配层。
- 代价：需要维护 Tauri/Rust 宿主、前端构建产物和宿主版本兼容矩阵。
- 安全影响：API Key 只进入 DGOS Secret Service；前端和普通 App 不得到系统钥匙串原始值。
- 运维影响：桌面发行包需要绑定 API/Worker/迁移版本；Web 需要独立部署 API、Worker、事务存储和对象存储。
- 部署影响：Web V1 必须提供 Web、API、Worker、PostgreSQL、Redis 和对象存储的本地 Compose 拓扑、持久卷和健康检查；桌面端可将 API/Worker/本地存储适配器随 macOS 包分发。
- 重新评估条件：目标平台原生能力无法覆盖、桌面自动更新/回滚失败，或运行证据显示宿主边界成为稳定性瓶颈。

本 ADR 已被 [ADR-0003 V1 技术栈与可替换运行时](0003-V1技术栈与可替换运行时.md) 取代；保留本文件用于追溯共用前端与桌面宿主边界的早期评审。

## 验证

- 同一前端应用包在 Web 和桌面打开相同路由并完成权限、Provider 配置和线性 AI Task 主链路。
- 桌面窗口、Dock/启动台、文件选择器和钥匙串能力通过宿主适配层调用，前端不直接读取系统秘密。
- 桌面 API/Worker 退出并重启后，任务状态可从 DGOS 任务服务恢复；Web 断线后可通过查询和事件订阅恢复。
- `V1-E2E-01`、`V1-E2E-05`、`V1-E2E-07` 在 Web 与桌面入口分别执行，并记录包版本、schema 版本和证据路径。
- Web 入口通过 Docker Compose 启动并通过健康检查；桌面入口在 macOS 上启动。Windows 适配只要求保留接口和架构边界，不计入 V1 门禁。
