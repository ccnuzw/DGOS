# V1 冻结决策

本表记录影响范围、协议和架构的一致性决策；新证据到达后追加新编号，不改写历史结论。

## D001（历史错误假设，已被 D013/D014 取代）以 DX OS 公共 Bridge 作为 V1 集成边界

- 状态：已被 D013 取代（仅保留为历史研究结论）
- 当前口径：本节只记录早期错误假设及其被取代的原因，不构成 DGOS 当前运行时、接口或验收依据；当前以 D013、D014 为准。
- 早期错误结论：曾假设 APP 使用 `window.dx.invoke`、V1 的 DX OS `ai.*`/Agent 协议以及 V2 的 DX OS `project.*`/Canvas 协议；不使用旧 `/api/canvas/*` 或自拼模型 endpoint。该假设已废弃，不是 DGOS 当前接口或验收依据。
- 来源：[DX OS 外部官网开发者中心摘要](../90-参考资料/DX-OS官网开发者中心摘要.md)。
- 后果：该错误假设会迫使 V1 依赖 DX OS 真实宿主或模拟宿主才能验收；旧项目实现只能做交互参考。当前 DGOS 由自己的桌面/Web 宿主和 API/SDK 验收，不需要 DX OS 宿主。

## D013 DGOS 是独立系统与应用平台

- 状态：已冻结
- 结论：DGOS 是全新、独立运行的系统，提供自己的系统壳层、应用规范、应用目录/商店、应用生命周期、权限边界和版本化系统服务。DX OS 只作为产品理念、交互和功能行为的参考，不是 DGOS 的宿主、运行环境、数据所有者或协议来源。
- 应用模型：无限画布、对话、文件、Skill/MCP 管理、天气等可作为独立应用接入；Skill、MCP 服务和 Canvas 节点也可作为受权限控制的扩展能力，不强制都建模为同一种应用包。
- 架构边界：DGOS 自行定义 app manifest、应用 API/SDK、身份与权限、项目/文件、模型/任务/产物和安装更新协议。DX OS 的 `dx-app/v2`、`window.dx.invoke`、`project.*`、`ai.*` 不构成 DGOS 约束，不能直接复制为接口契约。
- 原因：用户明确 DGOS 是全新系统，只借鉴 DX OS 理念，并需要承载按规范开发的多应用生态。
- 后果：产品蓝图、V1 范围、总体架构、接口契约、数据模型和版本路线图按独立系统重新基线；具体技术栈、进程/部署形态及 V1 内置应用组合需后续 ADR/产品评审冻结。

## D014 V1 平台基础属于 DGOS 自身

- 状态：平台基础边界已冻结；应用目录范围由 D030 修订；首发应用组合部分由 D018 取代
- 结论：V1 必须交付 DGOS 自有系统壳层、应用规范与运行时、最小应用目录、应用生命周期、权限边界及必要系统服务；DX OS 不提供 DGOS 的桌面、安装、数据或服务运行环境。
- 历史范围控制（已被 D030 修订）：早期仅要求系统预置应用发现、详情和启动及开发者本机测试安装，并将公开投稿审核放至 V6。当前普通用户可管理官方和管理员批准目录中的应用，开发者应用审核准入与安装生命周期属于 V1；评分、收费和规模化市场运营仍属 V6。无限画布及项目进入 V2，工作流/结构化资产/3D/协作继续按 D012 分期。
- 原因：DGOS 是独立系统，且其产品目标是让符合 DGOS 规范的应用能够安装并运行。
- 后果：V1 退出门禁改为独立系统的应用发现、安装、启动、更新/回滚和卸载闭环；目录准入和用户生命周期以 D030 为准，首发应用组合以 D018 为准，技术栈及进程拓扑仍待 ADR/专项讨论。

## D015 DGOS 采用独立应用平台与受控扩展运行时模型

- 状态：已冻结（设计方向；字段级 schema 和传输方式待 ADR 冻结）
- 结论：DGOS 参考 DX OS 开发者中心体现的“应用清单 + 运行时上下文 + capability broker + 项目/任务/Artifact 服务 + 扩展生命周期”模型，但由 DGOS 自己定义 manifest、SDK/API、权限、数据边界和安装协议。应用是 DGOS 的第一类产品实体；应用商店、文件/文件夹、天气、对话智能体、Skill 管理、MCP 管理和无限画布均可作为可启动应用承载。
- 边界：DX OS 的 `dx-app/v2`、`window.dx.invoke`、Bridge、内部接口、技术栈和旧项目 API 只作为研究资料，不进入 DGOS 公共契约。DGOS 应用通过自有 SDK/capability broker 调用系统能力，服务端重新校验权限；普通应用、受信应用和系统应用按不同信任级别运行。
- 依据：[DX-OS 开发者文档研究](../90-参考资料/DX-OS开发者文档研究.md)、[V1 DGOS 应用清单与运行时契约](../04-技术架构/当前版本/V1-DGOS应用清单与运行时契约.md)。
- 后果：V1 必须先冻结应用包校验、manifest 字段语义、窗口/系统上下文、数据与秘密边界、安装更新回滚和最小 SDK 能力；V2–V6 按路线图逐步接入项目、画布、工作流、资产、3D、插件和协作。此决策不冻结具体前端框架、进程拓扑、IPC/HTTP 传输或签名算法。

## D002 正确旧项目为 `infinite-canvas-ccnuzw`

- 状态：已冻结
- 结论：只读取 `/Users/apple/Progame/infinite-canvas-ccnuzw` 作为作者旧项目参考，不把其 Python/FastAPI、本地 API、浏览器存储和供应商直连当作新架构。
- 后果：后续截图和代码到达后，需在参考资料中追加映射，不回填为“已实现”。

## D003 V1 先做单用户闭环

- 状态：已冻结，首发范围由 D007 进一步分层
- 结论：V1 保持单用户闭环；多人协作、市场、批量队列和完整移动端归 V6 规划。登记功能可超过首发范围，但首发门禁只覆盖已冻结的核心闭环和平台最小支撑。
- 后果：不为未冻结的协作或生态需求提前设计第二套状态或存储语义。

## D004（历史研究命名，已被 D019/D021/D023 取代）AI 任务与 Agent 任务分离

- 状态：已被 DGOS 自有命名取代，仅保留为研究记录
- 早期研究记录：DX OS 外部规范曾将图片/视频/音频/转录写作 `ai.task.*`，将 Agent 后台写作 `task.*`。这些名称属于 DX OS 研究样本，不是 DGOS 公共契约。
- 当前 DGOS 口径：媒体和模型任务使用 `dgos.aiTask.*`；Agent/Skill/MCP 执行记录使用 `dgos.agent.*` 或对应的 DGOS 扩展执行 API；两者的 taskId、状态和取消语义不互换。
- 来源：DX OS 外部官网 APP 完整开发规范（仅作研究样本）。

## D005 第二轮复核新增模型配置与资产历史功能

- 状态：已冻结
- 结论：API 渠道/凭据/模型目录登记为 `V1-FR-007` 基础子集；工作流管理属于其 V2 高级子集。资产选择/生成历史/结果引用/删除保护登记为 `V1-FR-008`，整体移入 V2。它们是可独立验收目标，不并入单一 AI 提交步骤。
- 来源：[视频时间线第二轮复核](../90-参考资料/DX-OS视频时间线.md)。
- 后果：V1 功能总数为八项，新增高风险技术设计、E2E 和发布门禁关联；系统助手的首发边界由 D022 进一步冻结。

## D006 视频观察不冻结供应商名单

- 状态：已冻结
- 结论：视频中的 ModelScope、Agnes AI、RunningHub、ComfyUI 等名称只作为观察证据；V1 通过 DGOS 自有模型目录、工作流协议和配置状态选择能力，不把具体供应商写成必选依赖。
- 后果：后续截图或协议更新可增加/替换平台，而不改变 `V1-FR-005/007` 的公共边界。

## D007 V1 首发范围分层

- 状态：已被 D008 取代
- 结论：原分层已被 D008 修正；画布与资产历史不再进入 V1 首发。
- 原因：见 D008。
- 后果：E2E-06、插件扩展技术设计和相关风险仍可维护，但不阻塞 V1 首发完成。该历史决策中将系统能力视为 DX OS 宿主提供的结论由 D013/D014 取代。

## D008 先基础后画布

- 状态：已冻结
- 结论：V1 先交付 DGOS 独立系统平台最小闭环、应用生命周期、权限/Agent 接入、必要系统服务和经范围冻结的示范应用。创作能力按 V2 项目与画布基础、V3 可执行画布工作流、V4 结构化创作与资产、V5 3D/扩展、V6 协作生态逐级交付。
- 原因：画布依赖项目持久化、节点模型、任务状态、artifact 引用闭包、窗口承载和扩展隔离。先稳定这些基础契约，再实现画布可以减少架构返工。
- 后果：V1 不要求 DGOS Project API、画布节点、结果拖回画布、ComfyUI/GPU 工作流、资产删除保护或 3D 导演台；这些能力按路线图在 V2–V5 验收，协作生态在 V6 验收。

## D009 画布连接与整理采用确定性图算法

- 状态：已冻结（V2 设计输入）
- 结论：画布端口使用稳定 `portId` 和显式类型/基数；连接只允许 `output -> input`，默认数据图为 DAG；“整理连接节点”只布局选中子图且检测到环路时原子取消；“连接下游节点”采用预览后原子提交，动态端口先落盘再建边，不自动运行任务。
- 来源：[无限画布与项目-技术设计](../03-功能规格/V2/04-无限画布/02-无限画布与项目-技术设计.md)、Ep2 画布交互、旧项目端口拖拽和 `connections` 遍历行为。
- 后果：V2 实现不能把旧项目 `inputNodeIds/sourceNodeId` 或供应商类型判断直接作为新契约；端口矩阵、布局排序、批量连接和失败原因必须有集成/E2E 证据。V3 以后扩展端口仍须兼容这一基础规则。

## D010 节点运行快照与工作流迁移采用显式契约

- 状态：已冻结（V2 设计输入）
- 结论：画布节点分离保存配置、输入状态、运行状态、结果引用和布局状态；执行节点运行前生成不可变 `RunSnapshot`，结果按 `runId` 追加。工作流导出使用带版本、节点类型/端口快照和资源清单的 `WorkflowPackage`，导入执行解析—校验—预览—提交，失败不改变当前画布。
- 来源：[无限画布与项目-技术设计](../03-功能规格/V2/04-无限画布/02-无限画布与项目-技术设计.md)、旧项目循环/生成/导入导出行为复核。
- 后果：V2 实现不得把任务 ID、临时 URL、轮询游标或供应商私有路径写入可迁移项目结构；V3 的 AC11/AC12 必须有运行状态、幂等、秘密剔除、ID 重映射和原子回滚证据。

## D011 3D 导演台作为独立领域并以 artifact 回写画布

- 状态：已冻结（V5 专项设计输入）
- 结论：3D 导演台是画布中的独立节点和场景子工作区；场景对象、机位、全景、时间线、关键帧和导出由独立领域模型管理。截图和视频通过稳定 artifact 回写为新画布节点/边；导演台删除不删除已回写输出。导出使用固定场景/机位/时间线快照，默认 1280×720、30 FPS、H.264，具体能力以 DGOS Runtime 的能力握手为准。
- 来源：[3D 导演台专项](../03-功能规格/V5/04-无限画布/03-3D导演台专项-技术设计.md)、`infinite-canvas-tigerowo` 导演台功能文档和代码复核。
- 后果：V5 不得把 3D 对象展开为普通画布节点，也不得把 iframe 消息、浏览器缓存或内部渲染格式当作公共契约；AC13 需要覆盖场景恢复、关键帧事务、截图/导出失败保护和回写解耦。

## D012 创作能力按依赖拆分为 V2–V6

- 状态：已冻结
- 结论：不把无限画布、可执行工作流、结构化创作、3D/扩展和协作生态压缩到单一 V2。V2 只交付项目与画布基础，V3 交付画布工作流，V4 交付多维表格/资产/Agent/供应商节点，V5 交付 3D 导演台与插件模板，V6 交付协作、市场、批量队列和移动端。
- 原因：这些能力分别依赖项目持久化、任务与 artifact 状态、授权与资产闭包、渲染与扩展隔离、冲突合并和发布门禁；按依赖逐级稳定可以减少跨版本返工并保持每版可验收。
- 后果：功能编号继续保持稳定，版本归属以路线图和功能规格的分阶段表为准；后续实现、E2E 和发布门禁不得把高版本能力默认算入 V1 或 V2。

## D016 DGOS 扩展采用声明驱动、统一执行器和适配器隔离模型

- 状态：已冻结（设计方向；字段级 schema 和传输方式待 ADR 冻结）
- 结论：DGOS 将 App、Skill、MCP、Agent Tool 和 Canvas Node 视为可声明、可注册、可授权、可审计的扩展类型。扩展可以由同一个应用包提供，也可以独立安装，但身份、版本、秘密、启用状态、连接状态和运行状态分别保存。手动运行与 Agent 运行必须进入对应的 DGOS 统一执行器；适配器只负责把公开声明映射到执行器，不暴露 DGOS Runtime 内部 API。
- MCP 边界：bundled、system、external 只描述安装归属；MCP 配置、秘密、连接和工具发现分离。无凭据且健康检查通过的 bundled MCP 才能申请自动启动；需要凭据的服务保持待配置。工具绑定使用 DGOS 自有的结构化引用，并且必须来自已声明依赖，不能调用方任意替换。
- 数据边界：扩展通过 App/项目 capability 获取最小字段或 Artifact 引用，经过脱敏后执行，再由 App 校验并带并发条件写回。扩展不自动获得用户身份、Cookie、绝对路径、项目目录或秘密；持久执行使用 Task/Run，不用前台调用模拟恢复。
- 来源：[DX-OS 开发者文档研究](../90-参考资料/DX-OS开发者文档研究.md)、[DGOS 扩展声明与执行契约](../04-技术架构/当前版本/V1-DGOS扩展声明与执行契约.md)。
- 后果：V1 冻结扩展声明/注册、权限、Skill/MCP 管理、MCP 连接状态、工具目录和审计边界；V2 冻结项目/Artifact 作用域与 Canvas 基础，V3 冻结统一 Canvas Executor，V4-V5 再交付 Agent Workspace、供应商节点和第三方插件 SDK。DX OS 的字段、协议和文件名只作为研究来源，不进入 DGOS 公共契约。

## D017 吸收本地开发规范但保持 DGOS 自有契约

- 状态：已冻结（设计方向；容器、传输和字段 schema 待后续 ADR）
- 结论：重新读取的五份本地 DX OS 开发规范确认了 DGOS 需要具备的完整平台边界：静态应用入口、DGOS 运行时托管能力、应用隔离、特权应用白名单、AI Target/动态 descriptor 握手、Skill 包与子 Skill 身份、MCP 配置/秘密/连接/工具发现分离、协作房间独立协议，以及 Canvas Agent 的声明层—适配层—统一执行层。DGOS 吸收这些边界和开发者体验原则，但不兼容 DX OS 的协议名、字段名、文件名、Bridge、iframe 实现或技术栈。
- 依据：[DX-OS 开发者文档研究](../90-参考资料/DX-OS开发者文档研究.md)、[DX-OS 外部官网开发者中心摘要](../90-参考资料/DX-OS官网开发者中心摘要.md)、[V1 DGOS 应用清单与运行时契约](../04-技术架构/当前版本/V1-DGOS应用清单与运行时契约.md)、[五份本地规范](../../reference/完整开发规范.md)。
- 后果：V1 需把静态入口、等价隔离、普通/受信/系统应用差异、特权白名单、Target 握手和扩展声明纳入平台基线；协作保持 V6，Canvas Agent 按 V3–V5 交付。任何具体实现方案仍须以 DGOS 自有 ADR 和验收证据为准。

## D018 V1 首发应用、Provider 基础能力与身份演进

- 状态：已冻结
- 结论：V1 固定交付应用目录/商店、系统设置、开发者中心、文件、Skill 管理、MCP 管理、线性 AI 任务工作区和系统智能助手八项第一方应用。真实 API Provider 适配、凭据隔离、连通性验证、模型目录和能力标签属于 V1 平台基础；桌面端与 HTTPS Web 端共用前端应用包、设计系统、路由语义和版本化 API。V1 建立 UserProfile、Session 和主体作用域，正式登录进入 V2，组织/团队与共享开发进入 V6。助手动作覆盖范围原先记录为系统导航、查询和有限受控配置，现由 D031 扩展为大部分有公开契约的系统设置与应用配置；高风险动作仍须确认。
- 依据：[D018 详细决策](D018-V1首发应用与身份演进.md)。

## D019 V1 平台目标、Provider 协议扩展与官方 Skill/MCP 应用

- 状态：已冻结（技术实现与字段级 schema 待 ADR/代码验证）
- 结论：V1 桌面发行目标为 macOS；Windows 是后续桌面目标，V1 起保留可替换的宿主平台适配接口。V1 Web 入口必须支持 Docker Compose 本地部署。首批真实 Provider 协议为 `openai-compatible`，通过可扩展的 `ProtocolAdapterRegistry` 和版本化 `ProviderCapabilityDescriptor` 注册；新增协议只增加适配器，不改变前端 Provider/Model/AI Task 公共契约。V1 文本 AI Task 必须支持 SSE（或等价 DGOS 事件订阅）流式增量输出，断线可通过游标或查询恢复，最终状态以任务查询为权威。Skill 管理和 MCP 管理作为默认安装的 DGOS 官方应用交付，可安装、启用、停用、配置和扩展；系统设置只提供快捷入口和系统级摘要。
- 身份范围：V1 不交付正式账号登录和完整多用户功能，但 UserProfile、Session、`subjectType/subjectId`、权限、所有权和审计接口必须按未来多用户/组织模型设计；正式登录进入 V2，组织/团队与共享开发进入 V6。
- 依据：用户对平台目标、Provider 首发协议、流式输出和 Skill/MCP 应用化的确认；[V1 技术栈候选与专项讨论](../04-技术架构/当前版本/V1-技术栈候选与专项讨论.md)。
- 后果：产品范围、技术栈专项、Provider/AI Task/Skill-MCP 功能规格、路由、E2E 和测试策略必须包含上述约束；Windows、正式登录、组织协作和新增 Provider 协议不计入 V1 完成条件。

## D020 Provider 配置与模型目录采用显式两步流程

- 状态：已冻结（技术实现与字段级 schema 待 ADR/代码验证）
- 结论：V1 Provider 页面只要求名称、Base URL、协议类型和一次性 API Key 输入；API Key 写入 DGOS Secret Boundary，后续只返回脱敏状态。`validate` 只验证协议、地址、凭据和能力 descriptor，不隐式拉取模型；用户必须显式执行 `models.refresh` 才更新模型目录。V1 不提供 Provider 配置导入/导出，也不提供手动添加模型。
- 模型策略：拉取后的模型由 `ModelCapabilityPolicy` 管理 `assignedCapabilities`、`enabled` 和 `defaultFor`。只有 active Provider、available 模型、启用策略和匹配能力同时成立时，模型才进入对应任务入口；每个 Provider 每项能力最多一个默认模型，刷新不会自动启用模型。
- 依据：用户对 Provider 配置页面、模型拉取、能力分类和按任务筛选的确认；[模型平台与工作流配置](../03-功能规格/V1/07-模型与配置/01-模型平台与工作流配置.md)。
- 后果：Provider 配置、数据模型、OpenAPI、技术设计和 `V1-E2E-07` 必须保持验证/拉取分离；参考产品截图中的导入/导出和手动添加模型只作为 DX OS 事实，不进入 DGOS V1。

## D021 Provider 覆盖策略吸收 OpenAI 官方协议语义并分层交付

- 状态：已冻结（适配器字段和真实供应商 contract test 仍需实现验证）
- 结论：DGOS V1 冻结统一 `ProviderAdapter`、`ModelCatalog`、`ProviderCapabilityDescriptor` 和 DGOS 流式事件。首发协议为 `openai-compatible`，可用 provider preset 接入 OpenAI、Grok、DeepSeek、通义等通过 contract test 的兼容服务；适配器保留 `responses` 与 `chat-completions` operation profile，不假设所有兼容服务实现同一套端点。Anthropic Messages、Gemini native 和其他特定协议作为后续 Provider Pack 接入。Claude Code 不进入普通 Provider 页面，而作为 Agent/官方应用运行时接入。
- OpenAI Docs 明确的模型目录、SSE 增量事件和工具/MCP 可选能力只在 adapter 内映射：`response.output_text.delta`/`response.completed`/`error` 映射到 DGOS `text.delta`/终态/失败；模型的图片、视频、音频、函数调用或 MCP 能力必须由 descriptor 和真实 contract test 证明。
- 工具与 MCP 边界：V1 交付 MCP 官方应用的安装、连接、权限和工具发现；Provider 工具调用不能绕过 DGOS capability broker、用户同意和审计。工具调用的完整 Agent/画布体验按 V3–V5 交付。
- 依据：[Provider官方协议调研](../90-参考资料/Provider官方协议调研.md)、[OpenAI Models](https://developers.openai.com/api/docs/models)、[OpenAI Streaming API responses](https://developers.openai.com/api/docs/guides/streaming-responses)、[OpenAI Using tools](https://developers.openai.com/api/docs/guides/tools)。
- 后果：V1 路线图和 E2E 必须区分协议闭环、provider preset 和原生 adapter；不能把“支持 OpenAI 兼容”写成“支持所有 OpenAI 模型能力”，也不能将 Claude Code 当作 API Key Provider。

## D022（助手范围由 D031 扩展）DGOS 是通用应用操作系统，内置助手通过动作目录受控操作

- 状态：已冻结（动作 schema、Resolver 模型和确认 UI 的字段级细节待 ADR/代码验证）
- 结论：DGOS 的产品边界是通用、独立、可扩展的应用操作系统。Provider、Skill、MCP、权限、秘密、任务、事件、应用安装和生命周期属于 DGOS 底层平台能力；无限画布、音乐、天气、二维码、网盘、对话等属于遵守 DGOS manifest、SDK、权限和生命周期规范的应用。第一方与第三方应用都可以通过公开契约注册能力，系统统一管理安装、启停、升级、权限和审计。
- 助手：V1 提供默认安装的系统智能助手应用。快捷指令直接引用稳定 `actionId`；自然语言只产生已注册动作的候选和结构化输入。两种入口都必须经过 Action Registry、Capability Broker、确认策略和统一 Action Executor；助手不能读取应用私有状态、秘密、供应商凭据或调用未注册 API。
- 原 V1 范围：系统导航/查询、Provider/Skill/MCP 页面入口、有限系统设置动作、动作计划、风险确认、长任务查询/取消和脱敏审计。助手设置与应用配置范围现由 D031 扩展；项目/画布、资产和组织/共享仍按 V2–V6 的上游契约逐步开放。
- 原因：统一底层能力是 DGOS 承载多领域应用和未来生态的前提；动作目录使自然语言成为应用能力的受控入口，而不是全局特权通道。将助手与领域应用解耦可以避免每个应用重复实现 AI 控制层，也避免在画布等基础未稳定前暴露高风险副作用。
- 后果：新增 `V1-FR-009` 与 `V1-E2E-09`；manifest 增加 `actions` 声明；V1 API/OpenAPI 增加 Action Registry、计划、执行、查询和取消动作；应用运行时、总体架构、V1 路线图和实现状态必须保持该边界。动作版本、风险枚举、Resolver 上下文和确认凭证另行 ADR 冻结。有限设置动作边界已由 D031 取代。

## D023 V1 采用连接协议、能力协议与 Model Profile 三层模型

- 状态：已冻结（能力协议签名、来源信任、迁移和发布审批待后续 ADR/实现验证）
- 结论：DGOS 将 Provider 接入拆为连接协议、能力协议和 Model Profile 三层。连接协议负责 Base URL、鉴权、模型目录和连通性；能力协议使用 DGOS 自有 `dgos-capability/v1`，以声明式 `operations`、`workflows`、动态参数和素材规则描述真实 Intent；Model Profile 通过真实模型名/兼容别名绑定 capabilities、workflow、defaults、limits、uiSchemas 和 assets。只有三层均校验通过的模型才进入 AI 任务选择器。
- 安全边界：能力协议由白名单解释器执行，只允许有限声明式映射原语；禁止脚本、eval、Shell、函数体、任意 URL 拼接和按模型名称猜测参数。异步任务必须完成 submit/query/status/error/result/download 闭环，不能以单个 `completed` 状态代替产物确认。DX OS 的 `dx-protocol/v2` 只作为截图/示例研究材料，不作为 DGOS 公共契约。
- 原因：真实 Provider 的模型能力、动态 UI、图片/视频异步任务和上传下载协议无法由单一连接适配器稳定表达；分层后可增加协议和模型覆盖而不修改 AI Task 公共契约，同时避免把外部 JSON 变成任意代码执行入口。
- 后果：新增 `CapabilityProtocolRegistration`、`ModelProfile`、`ProtocolOperation`、`ProtocolWorkflow` 数据模型和 `CapabilityProtocolRegistry`；`dgos.provider.capabilityProtocols` 与 `dgos.model.resolve` 必须返回可执行闭环及 UI/素材描述。V1 只交付线性 AI Task 协议中心，画布节点和复杂多节点编排仍按 V3–V5 交付。

## D024 协议中心是开发者扩展面，Provider 设置是用户配置面

- 状态：已冻结（角色权限和发布审批细节待后续 ADR/实现验证）
- 结论：协议中心用于快速适配新 Provider 和模型，面向开发者/平台管理员，负责 Adapter、能力协议和 Model Profile 的注册、校验、测试、发布、停用和版本管理。普通用户不需要理解协议 JSON 或 operation 细节，只在 Provider 设置中选择已发布 Adapter，填写 Base URL 与 API Key/Token，验证连接，拉取模型，勾选启用并保存默认模型。
- 原因：协议中心解决扩展效率，Provider 设置解决日常使用；把两者混在一个页面会让普通用户承担供应商协议复杂度，也会扩大凭据和协议编辑权限。
- 后果：协议中心路由仅对开发者/平台管理员开放；普通用户只能读取已发布 Adapter 和匹配的 Model Profile。新协议发布不会自动迁移已有 Provider 配置，停用协议不删除配置但会阻止新任务并显示原因。

## D026 V1 收敛为平台控制面与一个参考 APP

- 状态：已冻结（当前产品范围）
- 结论：V1 不再按多个完整业务应用首发。平台控制面包括应用目录、系统设置、开发者中心、Skill/MCP 管理和系统智能助手；唯一业务示范 APP 为 DGOS AI 工作台，验证 Provider 配置、文本模型选择、真实文本任务、SSE 流式输出、任务状态、结果展示和错误恢复。文件、天气、对话智能体、无限画布、图片/视频/音频创作、批量队列、项目资产和完整商店体验按 V2–V6 分层交付。
- 原因：V1 的首要目标是建立可扩展 DGOS 底层能力，并用一个真实 APP 做端到端纵向验证；同时交付多个完整业务应用会分散平台基础建设和验收资源。
- 后果：V1 产品蓝图、版本路线图、版本总览、产品需求、功能索引/追踪、架构、E2E 和实现状态均以本决策为准；`D018` 中八项应用清单保留为历史基线，不再作为当前首发门禁。

## D025 DGOS 系统设置提供统一上下文，APP 权限与启动权限分离

- 状态：已冻结（字段级 schema、策略优先级和平台适配细节待 ADR/实现验证）
- 结论：DGOS 系统设置属于平台服务和默认官方设置应用，V1 统一提供外观、语言与地区、网络代理、网格、隐私安全和 APP 权限。设置通过 `SystemContextSnapshot` 注入所有应用；应用可以读取上下文和内容级偏好，但不能自行覆盖 DGOS 系统层的主题、倍率、窗口生命周期或网络出口。
- 语言语义：`uiLocale`、`effectiveLocale`、`regionFormat`、`assistantLanguage`、`projectContentLanguage` 分开保存。界面语言切换不自动翻译项目名称、文件名、正文、Skill 或应用私有数据。
- 网络语义：Provider 请求、模型拉取、Skill/MCP 在线导入和后台服务遵循统一 `proxyMode=system|manual|off`。代理凭据只进入秘密边界；保存后返回脱敏有效路由、受影响服务和 `restartRequired`，未重启服务不得宣称已经切换。
- 权限语义：`AppManifest.permissions` 与 `capabilityAllowlist` 只是声明和静态白名单。实际授权由 `subject + appId + capability + scope` 的 `AppCapabilityGrant`/`PermissionDecision` 决定，取值为 `allow/ask/deny`。`deny` 在执行层优先，`ask` 必须在副作用发生前确认；“允许打开 APP”不等于可调用 MCP、运行 Skill、写/删文件、发送通知或打开外部页面。
- 网格语义：`SystemGridSettings` 只定义 DGOS 系统层默认值和网格 token；V2 画布可以保存项目级可见性/布局，但不复制系统权限、外观或倍率语义。
- 原因：DGOS 是承载多个 APP 的独立应用操作系统，统一上下文和能力 broker 是保证应用体验一致、权限可审计以及未来 Web/桌面/Windows 宿主可替换的底层边界。
- 后果：新增 `SystemAppearanceSettings`、`SystemLocaleSettings`、`NetworkProxySettings`、`SystemGridSettings`、`AppCapabilityGrant` 和 `SystemContextSnapshot` 数据模型；`system.settings.read/write`、`dgos.system.context.read/events` 和 `permission.check/request` 进入 V1 公共契约。设置应用只管理 DGOS 系统配置，Provider/Skill/MCP 业务状态仍由对应官方应用维护。

## D027 V1 采用方案 A 技术栈并保留可替换运行时边界

- 状态：已冻结（技术设计基线；运行验证待实现证据）
- 结论：V1 采用 React + TypeScript + Vite 共用前端、Tauri 2 + Rust macOS 桌面宿主、Node.js LTS + TypeScript + Fastify 模块化 API、独立 Node/TypeScript Worker、Redis 队列/缓存、PostgreSQL、S3 兼容对象存储（本地 MinIO）和独立 `extension-runner`。Web 通过 Docker Compose 部署；业务语义以 OpenAPI 3.1、JSON Schema、HTTPS JSON、SSE 和 DGOS SDK 为准。
- 边界：Tauri command 只承载窗口、文件、钥匙串、菜单和生命周期等宿主能力；Provider Adapter、秘密、AI Task 和扩展执行不能在浏览器页面运行。首批 Provider 协议为 `openai-compatible`，通过 `ProtocolAdapterRegistry` 和版本化 `ProviderCapabilityDescriptor` 扩展。
- 可替换性：未来可按实测容量、故障隔离、合规或发布需要将 Worker 或部分 API 领域替换为 Go；必须继续兼容 React、Tauri 宿主接口、SDK、OpenAPI/JSON Schema、Provider Adapter、Task/Event 和 extension-runner 公共契约。Go 不是 V1 必选运行时。
- 备选：Electron + Go 保留为重评方案，完整比较见[技术栈专项](../04-技术架构/当前版本/V1-技术栈候选与专项讨论.md)；不在 V1 并行维护两套核心实现。
- 依据：[ADR-0003 V1 技术栈与可替换运行时](ADR/0003-V1技术栈与可替换运行时.md)。
- 后果：公共架构、工程环境、V1 版本总览和部署/测试文档按方案 A 同步；Tauri、Compose、SSE、秘密存储、真实 Provider 和扩展隔离仍必须用实现阶段证据验证，不能将本决策写成已通过运行测试。

## D028 V1 统一设计系统与跨应用交互契约

- 状态：已冻结（初始视觉 token 与像素值待真实 DGOS 截图和实现证据校准）
- 结论：DGOS 以 `Design Tokens`、公开 `dgos-ui`、`AppShell` 和 `Host Adapter` 作为所有第一方/第三方应用的界面基础。平台统一窗口、页签、主题、语言地区、显示倍率、权限提示、任务状态、通知、错误边界、命令面板、文件/秘密入口和无障碍语义；应用负责领域路由、数据、表格、画布、媒体预览和专用工具。应用只能通过 manifest 声明有限的领域 token 和 UI 能力，不能覆盖系统主题、字体、窗口生命周期、权限策略或系统状态。
- 跨端语义：macOS 桌面与 HTTPS Web 共用前端、路由、UI Kit、快捷命令、任务状态和错误语义；窗口、文件选择器、钥匙串、通知和生命周期的差异由 Host Adapter 承担。未来 Windows 必须实现等价宿主能力或明确降级状态，不得让应用按平台分叉业务逻辑。
- 视觉边界：参考 DX OS 的空间化窗口、多窗口、设置分组和管理密度，但不复制其品牌、颜色、协议、Bridge、运行时或视觉资产。V1 初始 token 采用中性底色、蓝色主强调色、有限材质和 4 px 间距系统；具体像素值可以在真实运行截图证明后通过新 ADR 调整。
- 交互不变量：所有可交互元素必须有可见状态、键盘路径和可访问名称；异步和副作用必须显示 loading、终态、错误、取消/恢复和可追踪 ID；危险动作二次确认；颜色不能是唯一状态信息；秘密、内部 URL、绝对路径和凭据不得进入界面、通知或截图证据。
- 原因：DGOS 要承载无限画布、文件、天气、网盘、二维码等不同类型 APP。若每个 APP 自建窗口、权限、任务和视觉系统，平台将失去统一性，跨端维护和第三方扩展成本会持续增加。将平台控制面与领域界面分开，可以在保持系统一致的同时允许领域创新。
- 依据：[V1 界面与交互规范](../04-技术架构/当前版本/V1-界面规范.md)、[DX-OS成熟软件截图证据](../90-参考资料/DX-OS成熟软件截图证据.md)、[DX-OS开发者文档研究](../90-参考资料/DX-OS开发者文档研究.md)、`ui-ux-pro-max` 的无障碍、响应式、交互状态和动效基线。
- 后果：V1 实现必须先建立 `packages/design-tokens`、`packages/dgos-ui`、`packages/app-shell`、`packages/host-adapter` 的边界，再实现平台应用和 AI 工作台；UI 验收需要增加双宿主、主题/倍率/中英文、键盘辅助技术、异步恢复和 manifest UI 校验证据。没有真实截图或运行结果时，不得宣称视觉回归、Tauri/Web 一致性或 Windows 适配已经完成。

## D029 V1 本地部署使用单一受控主体

- 状态：已冻结
- 结论：每个 macOS 本机安装或 Docker Web 部署默认使用一个受控主体；V1 不提供普通用户账户注册、独立登录或同一部署内多用户隔离，但 V1 提供绑定该部署受控主体的管理员控制面登录/会话。正式终端用户账号中心、多用户登录和个人账号生命周期进入 V2。
- 边界：`subjectType/subjectId`、资源所有权、Session、权限和审计仍按可扩展主体模型设计。单主体部署不等于可将主体身份硬编码或取消执行时授权检查。
- 来源：用户 2026-09-28 明确选择原决策清单第 1 项建议 A。

## D030 普通用户可从受信目录管理应用

## D032 Provider 验证失败时停用配置

- 状态：已冻结
- 结论：Provider 配置更新/验证失败时，该 Provider 必须转为不可用于新任务的停用状态；不得继续以旧活动模型策略接受新任务。模型目录和用户分类历史可以保留供诊断与恢复，但模型选择器应立即移除该 Provider 模型。
- 失败边界：验证失败不得触发任务提交或供应商任务调用；当前已提交任务按原 taskId 继续查询/终止，不回滚或伪造终态。重新验证成功后，仍须显式刷新目录并由现有策略筛选，方可重新进入任务选择器。
- 目录刷新失败：只将目录标为 stale/unavailable；因刷新失败本身不等于凭据/连接验证失败，现有 Provider 是否仍可调用由最后一次有效配置状态决定，不能把目录刷新动作当作重新验证。若刷新同时发现凭据/连接验证失效，则应用本决策停用 Provider。
- 来源：用户 2026-09-28 明确选择原决策清单第 4 项 B。
- 后果：取代 D020“仅新草稿失败且旧 active 保持有效”的相关解释及 `V1-FR-007/AC02`、接口契约和 `V1-E2E-07` 的旧有效配置保留断言；失败停用应为原子状态转换，不删除秘密引用、目录或策略历史。
