# D018 V1 首发应用、Provider 基础能力与身份演进

## 状态

历史决策，已由 D026 取代首发应用组合部分（产品范围与架构边界仍保留为背景）；平台目标、首发协议、流式任务和官方 Skill/MCP 应用的后续确认见 D019；具体技术栈、传输方式和认证供应商仍待专项 ADR。

## 背景

DGOS 需要同时支持桌面端和 HTTPS Web，且 V1 必须能够调用真实 AI 模型。此前文档将 Provider 配置写成基础模型配置子集，将首发应用组合留作产品评审，身份只在架构图中出现，容易导致真实模型调用、桌面/Web 共用前端和多用户边界被后置或各自实现。

## 决策

### 1. 原定 V1 八项第一方应用（历史基线）

1. 应用目录/商店
2. 系统设置
3. 开发者中心
4. 文件应用
5. Skill 管理
6. MCP 管理
7. 线性 AI 任务工作区
8. 系统智能助手

无限画布、对话智能体、天气和资产/表格应用不进入 V1 首发；它们按版本路线图接入，但仍遵守同一 DGOS 应用规范。D026 将当前首发收敛为平台控制面和 DGOS AI 工作台唯一业务示范 APP。

### 2. Provider 是 V1 基础平台能力

V1 必须交付可插拔的 `Provider Adapter` 边界，包含：Provider 配置、协议类型、Base URL 引用、凭据托管、连通性验证、模型目录刷新、能力标签和统一模型/任务调用契约。第一方应用不能直接访问供应商 endpoint、API Key、Authorization 或供应商任务 ID。Provider 列表不在 DGOS 前端写死，模型能力以握手和目录结果为准。

### 3. 桌面/Web 共用前端

桌面端和 HTTPS Web 端共用同一前端应用包、设计系统、路由语义和版本化 DGOS API。宿主适配层只处理窗口、文件选择、安全存储、回调和设备能力差异，不复制领域逻辑或应用协议。

### 4. 身份分阶段交付

- V1：建立 `UserProfile`、`Session`、`subjectType/subjectId` 和权限主体抽象；允许受控本地或适配器会话用于平台开发和验收。
- V2：交付正式登录、登出、会话续期、个人数据归属和安全回跳；桌面/Web 使用同一身份 API。
- V3–V5：项目成员和共享资源继续使用主体作用域，不把所有权写死为用户字符串。
- V6：交付 `Organization`、`Team`、`Membership`、成员角色、组织策略、共享开发和协作审计。

Session 不是权限授权。撤销会话不能删除用户、项目、Artifact 或应用安装记录。

## 原因

- 八项应用足以验证壳层、应用生命周期、扩展管理、文件选择、Provider、真实 AI Task 和受控动作闭环；系统助手只操作已注册且获授权的系统动作，避免把无限画布及其高依赖能力压入首发。
- Provider 适配是 AI Task 的前置依赖，必须先统一秘密、错误、模型能力和任务状态。
- 共用前端避免桌面与 Web 形成两套产品协议，降低后续画布和协作的迁移成本。
- 主体作用域提前稳定，正式账号和组织协作可以增量加入而不重写资源授权。

## 影响与约束

- V1 发布门禁必须包含至少一条真实 Provider 验证和 AI Task 调用链，并验证凭据不泄露。
- `ProviderConfig`、`ModelCatalog`、`AITask`、`PermissionDecision` 和路由矩阵必须与本决策同步。
- 技术栈、认证供应商、桌面容器、Web 部署和具体 Adapter 数量不由本决策冻结，下一轮专项讨论后另立 ADR。
- 任何把 Provider、正式登录、组织协作或无限画布提前/后移的变更，必须更新版本路线图、需求追踪、接口/数据契约和验收门禁。
