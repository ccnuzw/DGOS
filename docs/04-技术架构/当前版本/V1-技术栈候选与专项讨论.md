# V1 技术栈候选与专项讨论

- 状态：Accepted baseline（方案 A）；方案 B 保留为 Proposed alternative
- 日期：2026-09-27
- 关联决策：D018、D019、D026、D027
- 关联 ADR：[ADR-0003 V1 技术栈与可替换运行时](../../06-决策记录/ADR/0003-V1技术栈与可替换运行时.md)

## 1. 评审目标

 V1 技术栈必须同时支持 macOS 桌面端与 HTTPS Web，复用同一套前端应用包、设计系统、路由语义和 DGOS API，并为真实 API Provider、秘密隔离、应用运行时和后续 V2–V6 扩展留下稳定边界。Web V1 必须能够通过 Docker Compose 在本地部署。Windows 是后续桌面目标，宿主适配层从 V1 起保留跨平台边界。技术选型不能把 DX OS 或旧项目的技术栈当成前置约束。

本文记录已接受的方案 A 基线、保留的方案 B 备选及其比较依据。方案 A 的接受结论见 [ADR-0003](../../06-决策记录/ADR/0003-V1技术栈与可替换运行时.md)；本文不把规划或静态评审当作运行验证证据。

## 2. 不可变约束

1. 桌面与 Web 使用同一套前端业务包和设计系统；平台差异只能位于宿主适配层。
2. 应用只能通过 DGOS SDK/API 和 capability broker 访问系统能力。
3. Provider Adapter、秘密服务和异步任务执行不能运行在浏览器页面中。
4. V1 采用模块化单体优先，但 Provider/扩展执行必须保留独立进程边界。
5. HTTP 字段以 OpenAPI 为机器可读权威；IPC 或桌面本地传输不能产生第二套业务语义。
6. V1 的 UserProfile、Session 和 `subjectType/subjectId` 不能被本地存储方案锁死为不可迁移的单用户模型。
7. V1 桌面发行目标为 macOS；Windows 作为后续宿主目标，窗口、文件、钥匙串和生命周期能力必须通过可替换的平台适配接口提供。
8. Web V1 必须提供可复现的 Docker Compose 本地部署形态，至少包含 Web、API、Worker 及其本地依赖的健康检查和配置入口。
9. 首批 Provider 协议为 `openai-compatible`；协议注册表和能力描述符必须可扩展，新增协议不得要求前端改写业务契约。
10. V1 文本 AI Task 必须支持 SSE（或等价 DGOS 事件订阅）流式增量输出，最终任务状态仍以查询 API 为权威。
11. Skill 管理和 MCP 管理以默认安装的 DGOS 官方应用交付；系统设置可提供快捷入口，但不能替代应用化管理界面。

## 3. 两套完整方案

两套方案都必须遵守以下不变边界：

- React/TypeScript 业务前端同时被 Web 和桌面入口消费；桌面宿主不能复制一套业务页面。
- 应用、Provider、Skill、MCP 和系统助手只能通过 DGOS SDK/API、事件和 capability broker 访问平台能力。
- Provider Adapter、秘密服务、异步 Worker 和扩展执行不能运行在浏览器页面中。
- HTTP/OpenAPI 是业务语义的唯一机器可读权威；桌面 IPC 只能承载宿主能力或转发同一套 API 语义。
- V1 采用模块化单体优先；只有扩展执行、秘密边界或资源曲线需要时才形成独立进程。
- Web 必须可由 Docker Compose 在本地启动；桌面必须从 V1 起保留 Windows 宿主适配接口。

### 3.1 方案 A：Tauri 2 + TypeScript 贯通（推荐）

这是以 V1 交付速度、双端复用和统一类型为第一目标的方案。

| 层 | 选型 | 运行边界 |
| --- | --- | --- |
| 前端 | React + TypeScript + Vite；pnpm workspace；共享 `packages/ui`、`packages/sdk`、`packages/app-runtime` | Web 和 Tauri 共同消费同一业务包 |
| 桌面 | Tauri 2 + Rust Shell | 只负责窗口、菜单、Dock/托盘、文件选择器、钥匙串和本地服务生命周期 |
| API/运行时 | Node.js LTS + TypeScript + Fastify 模块化单体 | 提供版本化 HTTP API、SSE、Provider/Task/App/Permission 等领域模块 |
| Worker | Node.js/TypeScript 独立 Worker；Redis 适配器和可替换队列接口 | 执行 Provider 调用、模型拉取、安装和导入任务 |
| 扩展 | 独立 `extension-runner` 进程，通过受限 JSON-RPC/stdio 或本地 IPC 调用 | Skill/MCP/Agent 不得读取核心进程内存或明文秘密 |
| 存储 | PostgreSQL + S3 兼容对象存储（本地 MinIO）+ Redis | 分别承载权威元数据、二进制和队列/缓存 |
| 部署 | Web 反向代理 + API + Worker + PostgreSQL + Redis + MinIO 的 Compose 拓扑；桌面可随包带本地服务 | 两个入口共享 API 与事件契约 |
| 测试 | Vitest/Node 集成、Playwright Web E2E、macOS 桌面 E2E、OpenAPI contract test | 同一 AC 在两个入口复用业务断言 |

**优势**

1. 前端、API、Worker、SDK 和类型定义主要使用 TypeScript，V1 的 Provider、SSE、错误映射和任务状态更容易保持一致。
2. Tauri 的桌面包和常驻资源开销通常低于 Electron，更贴合 DGOS 的系统壳层目标。
3. Rust Shell 把系统钥匙串、窗口和文件能力隔离在宿主边界，应用业务不需要接触原生 API。
4. 未来新增 Provider 协议可以先作为声明式配置或独立 Runner 接入，不必改写前端应用。

**代价与风险**

1. 团队必须维护少量 Rust 代码，桌面打包、签名、自动更新和 macOS 权限需要真实验证。
2. Tauri 的插件和跨平台原生能力要建立自己的适配接口，不能把某个插件 API 当作 DGOS 公共契约。
3. 桌面随包启动 API/Worker 时，需要处理迁移、端口、进程退出、升级和任务恢复。
4. Node Worker 和扩展 Runner 仍要限制 CPU、内存、网络出口和子进程权限。

### 3.2 方案 B：Electron + Go 核心服务（备选）

这是以桌面生态成熟度、静态服务二进制和后续高并发任务为第一目标的方案。

| 层 | 选型 | 运行边界 |
| --- | --- | --- |
| 前端 | React + TypeScript + Vite；共享 UI/SDK/路由包 | Web 与 Electron Renderer 共同消费 |
| 桌面 | Electron；主进程只负责窗口、菜单、协议注册和本地服务生命周期 | Renderer 通过预加载桥接调用宿主能力，禁止启用 Node 集成 |
| API/运行时 | Go 模块化单体（标准 `net/http` 或 chi）；OpenAPI 生成类型和路由骨架 | 承载 Provider、Task、App、Permission、Secret Gateway 等核心领域 |
| Worker | Go Worker；Redis Streams/BullMQ 等队列由 Go 适配器封装 | 处理 Provider 调用、轮询、SSE 事件和安装任务 |
| 扩展 | 独立进程，通过版本化 JSON-RPC/stdio；扩展可以用 Go、Node 或其他语言实现 | 核心只接受声明式 manifest、事件和受控结果 |
| 存储 | PostgreSQL + S3 兼容对象存储 + Redis | 与方案 A 相同，公共数据模型不变 |
| 部署 | Web 反向代理 + Go API + Go Worker + PostgreSQL + Redis + MinIO 的 Compose 拓扑；Electron 随包携带静态二进制 | 桌面/Web 只共享 HTTP、SSE 和 SDK 语义 |
| 测试 | Go 单元/集成测试、TypeScript 前端测试、Playwright 双入口 E2E、OpenAPI contract test | 需要维护 Go/TypeScript 两侧的契约生成与兼容检查 |

**优势**

1. Go API/Worker 可以编译为单一静态二进制，桌面随包分发和服务器部署的运行时依赖较少。
2. 并发任务、超时、取消、限流和长时间 Worker 的资源行为更容易做出稳定上限。
3. Electron 的窗口、自动更新、系统菜单、协议注册和 Windows 支持生态成熟，后续桌面平台扩展阻力较小。
4. 扩展 Runner 通过进程协议接入后，可用 Node、Go 或其他语言实现，适合未来第三方生态。

**代价与风险**

1. Electron 的包体和内存开销更高；DGOS 的多窗口和多个应用启动后，资源治理必须单独设门禁。
2. 前端 TypeScript 与 Go 服务之间需要维护 OpenAPI/JSON Schema 生成链、错误映射、事件类型和版本兼容，V1 交付速度会慢于方案 A。
3. Provider Adapter、协议中心和扩展 SDK 需要同时维护 Go 核心接口与跨语言进程协议，调试链更长。
4. Electron 主进程权限面较大；预加载桥、上下文隔离、自动更新签名和本地服务启动顺序必须经过安全测试。
5. 若桌面端把 Go 服务打包进 Electron，迁移、端口、崩溃恢复和日志收集仍需一套与 Web 不同的发行编排。

## 4. 方案逐项比较

评分为 1–5 分，5 分表示更适合 DGOS 当前目标；权重用于说明取舍，不代表已经完成性能测试。

| 评审维度 | 权重 | 方案 A：Tauri + TS/Node | 方案 B：Electron + Go | 评审说明 |
| --- | ---: | ---: | ---: | --- |
| V1 交付速度 | 20% | 5 | 3 | A 共享语言和类型更多，Provider/SSE/SDK 实现链更短 |
| Web/桌面业务复用 | 15% | 5 | 4 | 两者都复用 React；B 的宿主桥接与服务契约分层更多 |
| macOS 系统壳层 | 10% | 4 | 5 | B 的 Electron 桌面生态更成熟；A 需要验证 Tauri 插件与发行流程 |
| Windows 后续适配 | 10% | 4 | 5 | B 的桌面生态经验更广；A 通过宿主接口也可保留目标能力 |
| 运行资源与包体 | 10% | 5 | 2 | Tauri/Rust 壳层通常更轻；B 需要为多窗口/多应用设资源预算 |
| Provider/协议扩展 | 15% | 5 | 4 | A 可复用 TypeScript descriptor/SDK；B 的跨语言协议边界更严格但成本更高 |
| Worker/长任务治理 | 10% | 4 | 5 | Go 对常驻并发和静态部署更有优势；A 需要明确 Node 进程配额 |
| 团队维护复杂度 | 10% | 4 | 3 | A 是 TypeScript + Rust；B 是 TypeScript + Rust/Node Electron + Go |
| **加权结果** | **100%** | **4.55** | **3.85** | 作为技术评审基线，不替代实测 |

### 4.1 对关键 DGOS 能力的影响

| 能力 | 方案 A | 方案 B | 必须保持的公共语义 |
| --- | --- | --- | --- |
| Provider 配置/验证/模型拉取 | Fastify 领域模块 + TypeScript Adapter | Go 领域模块 + Go Adapter | `Provider`、`ModelCatalog`、能力分类和错误码不变 |
| 文本流式 AI Task | Node Worker 发布 SSE；查询 API 为最终权威 | Go Worker 发布 SSE；查询 API 为最终权威 | `queued/running/succeeded/failed/canceled`、断线恢复、幂等和取消语义不变 |
| Skill/MCP 官方应用 | Node extension-runner 起步，协议独立 | 多语言 Runner 更自然 | manifest、权限、秘密句柄、审计和生命周期不变 |
| 系统助手 | TypeScript Action Registry 与 Resolver | Go Action Registry，前端 SDK 不变 | 所有动作都经过 capability broker 和确认策略 |
| 桌面钥匙串 | Tauri Rust 插件/适配器 | Electron 主进程原生模块/适配器 | API Key 不进入 Renderer、日志或普通 API 响应 |
| Docker Web | Node 服务容器 | Go 静态服务容器 | Compose 服务名、健康检查、卷和环境变量契约不变 |
| 多用户/组织预留 | PostgreSQL schema 与主体字段 | 相同 | `subjectType/subjectId`、审计和资源所有权不绑定单用户实现 |

### 4.2 选择建议

当前建议将**方案 A 作为 V1 开发基线**，原因是 V1 的最大风险是平台纵向闭环尚未建立，统一 TypeScript 能缩短 Provider、真实流式任务、前端 SDK 和双入口 E2E 的反馈周期。方案 B 不是错误方向，适合以下条件成立时重评：

- 预计 V1 就需要大量常驻并发任务，Node Worker 的资源上限经实测无法满足；
- 团队已有稳定的 Go 服务、OpenAPI 生成和跨语言发布能力；
- Electron 的自动更新、Windows 发行或现成原生模块是硬性要求；
- 实测显示 Tauri 的窗口、钥匙串、文件和签名能力不能覆盖 DGOS 宿主验收。

如果选择方案 B，仍应保留 React/TypeScript 前端、OpenAPI/JSON Schema、Provider Protocol Registry、扩展进程协议和 capability broker，不应因为更换服务端语言而改写 DGOS 产品契约。

## 6. 关键运行边界

### 6.1 前端与宿主

```text
Web:     Browser -> HTTPS API/Events -> DGOS API/Worker
Desktop: Tauri Shell -> bundled dgos-api (loopback/host adapter)
                    -> same API/Events contract -> Worker/Provider Adapter
```

桌面端可以把 API、Worker 和本地存储适配器打包在同一个发行包中，但前端只能使用同一套 SDK 语义。Tauri command 只用于宿主能力（窗口、文件选择器、钥匙串、系统菜单等），不能承载一套绕过 DGOS API 的业务接口。

### 6.2 Provider Adapter

V1 首批协议适配器为 `openai-compatible`。协议不是前端枚举，而是服务端注册表中的可配置适配器。每个适配器发布 `protocolType`、配置 schema、能力描述符 schema、模型目录映射、任务映射、流式事件映射和错误分类；新增协议只需注册新的适配器并映射到既有 DGOS Provider/Model/AI Task 契约。

`ProviderAdapter` 至少提供以下逻辑操作：

- `validate(configRef, requestId)`：使用 Secret Service 取短时句柄，返回脱敏健康状态。
- `listModels(configRef, requestId)`：返回 DGOS `ModelCatalog`，供应商模型 ID 只作为受控映射保存。
- `submit(taskSnapshot, requestId)`：由 AI Task Worker 调用，不能由浏览器调用。
- `poll(taskId, requestId)` / `cancel(taskId, requestId)`：把供应商状态映射为 DGOS 状态。
- `writeArtifact(output, artifactContext)`：输出先写入暂存对象，再提交 artifact 元数据和引用。

适配器还必须声明 `capabilityDescriptor`，至少包括输入类型、输出类型、是否支持文本流式、任务模式、取消能力和模型目录来源。能力变化以版本化 descriptor 返回，前端不得根据供应商名称推断能力。

适配器必须支持超时、重试上限、幂等键、错误分类、限流和审计；不得把供应商私有响应原样写入公共 API 或项目文档。

### 6.3 秘密与身份

V1 的本地受控会话可以由桌面宿主或部署侧身份适配器建立，但所有服务接口仍携带标准主体上下文。V1 不交付正式账号注册、登录、登出和跨设备身份同步；接口、Session、资源所有权和审计字段必须按多用户模型设计。V2 接入正式登录时，只替换身份认证适配器和会话续期流程，不改写权限、资源所有权和审计字段。V6 增加组织/团队主体时，继续使用 `subjectType/subjectId`。

## 7. 候选决策点比较

| 决策点 | 方案 A（推荐） | 方案 B | 方案 C | 当前结论 |
| --- | --- | --- | --- | --- |
| 桌面宿主 | Tauri 2 | Electron | 浏览器/PWA | Tauri 2；Electron 只有在原生模块或团队能力证明必要时重评 |
| 后端运行时 | Node + Fastify | NestJS | Go | Node + Fastify；需要先验证 Worker 与扩展隔离，不因共享类型单独牺牲边界 |
| API 传输 | HTTPS JSON + SSE | GraphQL + WebSocket | gRPC + BFF | HTTPS JSON + SSE；V2 协作另行评估 WebSocket/CRDT |
| 任务队列 | Redis 适配器 | PostgreSQL 队列 | 云厂商队列 | V1 保留队列接口，先采用可本地运行的 Redis 方案 |
| 扩展隔离 | 独立进程 + capability | 容器/微虚拟机 | 进程内插件 | 独立进程；容器级隔离在第三方不可信扩展进入 V5/V6 时重评 |
| 秘密存储 | 宿主钥匙串/KMS 适配器 | 仅环境变量 | 应用本地加密文件 | 钥匙串/KMS；环境变量只作为开发夹具，不作为产品默认 |

## 8. 需要在技术栈评审中确认的问题

1. 技术 ADR 需要验证 Tauri 2 在 macOS V1 的窗口、文件和钥匙串能力，以及 Windows 后续适配接口的可行性。
2. Web Docker 本地部署需要冻结 Compose 服务拓扑、持久卷、健康检查和开发/生产配置边界。
3. 需要冻结 `ProtocolAdapterRegistry`、`ProviderCapabilityDescriptor` 和 `openai-compatible` 的字段级 schema，并补充机器可读 OpenAPI/JSON Schema。
4. 需要验证 SSE 文本增量、断线恢复和最终任务终态在桌面/Web 两个入口的一致语义。
5. Skill/MCP 官方应用的安装来源、版本签名和扩展 Runner 隔离策略需要在应用平台 ADR 中冻结。
6. 团队是否接受 TypeScript 贯穿前端、API 和 Worker；若 Provider 或扩展需要 Rust/Go，边界应以独立进程适配器接入，而不是把多语言直接混进核心领域模块。
