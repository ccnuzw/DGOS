## Fixture 分层

1. `w2-03` Web fixture 通过独立管理 fixture 提供真实 session、API、Worker、PostgreSQL、Redis；Provider TLS upstream 是确定性本地服务。它验证 DGOS 链路，不代表外部 Provider。
2. FR-003 fixture 使用随机 database、Redis namespace、签名/凭据目录和 MCP ID。正向安装与“已安装 MCP”用例必须独立初始化，禁止依赖上次运行的状态。
3. FR-002 lifecycle fixture 测试签名、路径穿越、健康失败、rollback、数据保留和不可卸载拒绝；浏览器入口另行真实执行。
4. Native GUI fixture 使用随机 Keychain service、临时 workspace 和 loopback API。Native Task/Artifact 证据必须来自当前候选 Workbench，不接受仅有 native session bridge 的 smoke。
5. 每个 fixture 写明被模拟的边界、真实组件、run ID 和 teardown readback；日志不得存 credential、token、prompt 私密内容或 artifact 正文。

## 最终判定规则

- `PASS`：所有 required 行真实执行、无 skip、source drift=false、cleanup 通过，且 Web 和 Native 各自达到 AC。
- `FAIL`：执行断言失败、命令非零、秘密扫描发现 confirmed-secret/ambiguous 或 migration/docs 必需门禁失败。
- `BLOCKED`：缺候选构建/fixture/授权凭据/Native handshake 前置条件，或运行环境缺失；blocked 不计为通过。
- `INCOMPLETE`：命令成功退出但目标测试未运行、被 skip 或只有静态证据。

当前基于 W3 证据的准备结论：FR-002/API lifecycle 有局部 PASS；FR-003 Skill 分支有局部 PASS；FR-009 UI 与 Provider 未知提交仍有失败；Native Workbench handshake、Task、Artifact 未验证。故当前尚不满足 V1 MVP 最终 PASS 条件。
