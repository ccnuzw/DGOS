## 2. 产品概述

### 2.1 一句话

DGOS 是一个全新的、独立运行的桌面与 Web 应用操作系统，提供应用运行环境、应用商店、系统服务、统一权限与可扩展的应用规范。AI 创作是首批应用和系统能力的重点场景，但不是 DGOS 的产品边界；天气、音乐、二维码、网盘、文件管理和其他符合规范的应用都可以运行在同一平台上。

### 2.2 定位

DGOS 借鉴 DX OS 的桌面、窗口、应用商店、开发者体验和模块化应用理念，但不运行在 DX OS 内，也不依赖 DX OS 的 Bridge、数据服务或技术栈。DGOS 自己负责系统壳层、应用规范与运行时、应用目录/商店、应用生命周期、身份/会话、权限、秘密、Provider、扩展注册和系统事件；应用通过 DGOS manifest、运行时上下文和 capability broker 使用受控系统能力。无限画布、对话智能体、文件/文件夹、Skill 管理、MCP 管理、天气等作为 DGOS 应用安装和运行。内置智能助手是 DGOS 官方系统应用，使用统一动作目录通过自然语言或快捷指令操作已授权的应用和系统能力，不绕过权限或直接读取应用私有状态。DGOS 面向桌面与 HTTPS Web 提供同一套前端应用包、设计系统、路由语义和版本化 DGOS API，不是 DX OS 的子应用或创作工作台。具体服务拆分和技术栈在架构决策冻结前保持开放。

### 2.3 愿景

让用户能在一个可扩展的应用操作系统中发现、安装、组合和操作不同领域的应用；在 AI 创作场景中，再从想法、素材和提示词出发完成编排、生成、复用、分享和扩展。第三方开发者可以通过公开规范安全地贡献应用、节点、Skill 和 MCP 能力。

## 3. 背景与问题

### 3.1 业务背景

视频、DX OS 外部官网开发者资料和截图展示了 DX OS 的桌面、开发者中心、应用、Skill/MCP 配置和无限画布创作。本项目将这些内容作为产品行为和交互证据；其 `dx-app/v2`、`window.dx.invoke`、`project.*` 与 `ai.*` 是 DX OS 自有协议，只作为研究材料，不作为 DGOS 的接口、运行时或架构约束。旧项目也只用于观察产品行为，不继承其架构或技术栈。

### 3.2 用户痛点

| 痛点 | 现状做法 | 代价 |
| --- | --- | --- |
| 创作上下文分散 | 文件、提示词、结果在多个工具之间切换 | 难以复现与迭代 |
| AI 能力接入不统一 | 每个项目自行拼接模型 API | 凭据、状态和错误处理不一致 |
| 开发者扩展成本高 | 需要理解 DGOS 内部实现 | 应用难以安装、审计和升级 |
| 系统能力入口分散 | 不同应用各自实现设置、快捷操作和外部能力接入 | 用户难以用统一方式发现和操作功能 |

### 3.3 解决方案

DGOS 提供应用运行时、统一权限/秘密/任务/事件/Provider/扩展服务，以及项目化的无限画布、节点化输入输出、统一异步 AI 任务、系统 Agent 能力接入和可声明权限的插件机制。内置助手通过注册动作目录把自然语言和快捷指令映射到这些公开能力；每条链路都保留输入、状态、产物引用和错误结果。

## 4. 产品目标

### 4.1 业务目标

- 用户能够在一个项目中完成“素材 → 提示词/配置 → 生成 → 结果整理”的闭环。
- 第三方应用和扩展可以只依赖公开 DGOS 协议完成安装、运行和卸载，不读取系统服务内部状态。
- 平台能力与应用业务分层：Provider、Skill、MCP、权限、秘密、任务、事件、安装和生命周期由 DGOS 统一管理；应用通过契约消费能力，不复制一套私有平台。
- 任何应用都可以按规范注册可发现动作，供用户界面、快捷指令和内置助手调用；动作调用仍由 capability broker 做主体、权限、风险和审计校验。
- V1 桌面端目标为 macOS，Web 端可通过 Docker Compose 本地部署；两者使用同一套前端应用包和 API 语义，Windows 通过后续 DGOS 平台适配层接入。
- 用户身份、会话和主体作用域先建立稳定边界，后续可扩展到组织/团队而不改写资源所有权模型。

| 指标 | 适用版本 | 当前基线 | 目标 | 口径与样本 | 验证方式 |
| --- | --- | --- | --- | --- | --- |

### 5.2 权限原则

- 权限由 DGOS 自有应用清单与权限服务定义，密钥由 DGOS 的安全边界管理，应用不得读取明文秘密或内部凭据。
- 项目与应用数据由 DGOS 自有数据服务管理；存储实现和 API 形式属于待冻结的架构决策。
- 外部输入、动态插件、AI 产物和文件导出必须有明确权限、状态和失败路径。

### 6.0.1 核心业务流程

| 流程 | 参与角色 | 触发与前提 | 主要步骤 | 成功终态 | 失败与恢复 | 适用版本 |
| --- | --- | --- | --- | --- | --- | --- |
| 文本任务 | 管理员、AI 工作台用户 | Provider 已配置、任务权限有效 | 验证、刷新目录、提交、订阅、查询、读取 | task 唯一终态与产物可见 | 断线恢复原 taskId；失败无伪造产物 | V1 |
| 应用测试安装 | 开发者、用户 | 有旧版或可安装包 | 校验、暂存、健康检查、提交、启动 | 活动版本可启动 | 失败回滚旧版并保留用户数据 | V1 |
| 助手受控动作 | 用户 | 官方助手和动作目录可用 | 发现、计划、确认、执行、审计 | 运行结果可查询 | 拒绝/取消不执行目标副作用 | V1 |
| 项目到协作 | 创作者、协作者 | 上游版本契约通过门禁 | 保存、运行、授权、扩展、共享 | 对应版业务终态可验证 | 各版处理冲突与回滚 | V2–V6 |

1. **V1 首次文本任务**：用户从桌面打开 AI 工作台，管理员先配置并验证 Provider、显式刷新模型目录，用户选择已启用的文本模型并提交。Task 服务返回 taskId，事件流展示增量，终态查询与产物读取确认结果；任务失败时工作台保留输入和原 taskId，不伪造成功产物；Provider 验证失败则停用 Provider、阻止新任务，已提交任务仍按原 taskId 收敛。见 `V1-E2E-05/07`。
2. **V1 应用测试安装**：开发者从开发者中心提交清单与包，平台校验声明及权限、暂存、健康检查，再提交活动版本。校验或健康检查失败时保留旧活动版本与用户数据，并给出可查询原因。见 `V1-E2E-02`。
3. **V1 助手执行**：用户从系统助手选择快捷指令或自然语言动作，目录先过滤不可用/无权动作；需确认的动作在执行前显示计划。拒绝、取消或 Provider 不可用时不能产生目标副作用，运行与审计仍可查询。见 `V1-E2E-09`。
4. **V2–V6 演进**：项目保存恢复 → 画布运行回写 → 资产授权复用 → 3D/插件 → 协作分发，每一步以对应版本独立规划和门禁为准，不把后续终态计入 V1。

### 6.2 首版必须做

- 基础闭环：`V1-FR-001`、`V1-FR-005`、`V1-FR-007`，其中 FR-005 交付线性任务，FR-007 必须包含真实 API Provider 适配、凭据隔离、连通性验证、模型发现和能力标签。
- 平台最小支撑：`V1-FR-001`、`V1-FR-002`、`V1-FR-003`，交付 DGOS 自有系统壳层、应用规范与生命周期、应用目录、权限和必要系统服务的最小闭环。
- V1 不交付无限画布、项目资产历史和 Canvas 插件；这些能力依赖基础层稳定后按 V2 项目基础、V3 画布工作流、V4 结构化创作、V5 3D/扩展和 V6 协作生态逐级实现。
- V1 首发交付收敛为平台控制面和一个业务示范 APP：应用目录/商店、系统设置、开发者中心、Skill/MCP 管理和系统智能助手组成平台控制面；目录包含官方发布和管理员批准的应用，支持最小审核准入及普通用户安装/更新/卸载，并按应用声明预装是否可卸载；唯一业务示范 APP 为 DGOS AI 工作台，负责 Provider 配置、文本模型选择和真实文本任务。Skill/MCP/助手应用默认随 DGOS 安装，可独立管理、扩展和受控调用。完整账号中心进入 V2，组织/团队和共享开发进入 V6。Provider 首批支持可配置的 `openai-compatible` 协议，文本任务支持流式输出。

### 6.3 首版暂不做：DGOS 独立平台边界

- DGOS 是全新的独立系统平台；V1 及后续版本都不把 DX OS 作为宿主、运行环境、兼容目标或服务依赖。DGOS 不实现 DX OS 兼容层，不运行在 DX OS 之上，也不复用 DX OS 私有服务、Bridge、内部协议、数据模型或技术栈。DGOS 自行提供系统壳层、应用运行时、应用规范、权限、Provider、任务、扩展和数据服务。V1 暂不做移动端完整体验、规模化商店运营/计费、正式账号中心、组织/团队协作、图片/视频/音频创作、无限画布和对旧版 `/api/canvas/*` 私有 API 的兼容。V1 只预留多用户主体、Session、权限和接口扩展，不交付完整多用户功能。

### 6.4 后续增强范围

- 无限画布与项目、项目资产与生成历史、Canvas 插件与模板扩展、FR-005/007 的画布和高级工作流子集、插件/模板市场、多人协作项目、批量任务队列、生产级观测和更完整的发布审核自动化，按 V2–V6 分阶段推进，详见[版本路线图](版本路线图.md)。V1 的最小审核准入和批准目录生命周期不重复计入 V6；V6 承接规模化投稿运营、评分、收费和商业分发。

### 7.1 应用化承载模型

DGOS 的用户可见能力统一通过应用目录、安装状态、窗口和权限入口承载。应用商店、文件/文件夹、天气、对话智能体、Skill 管理、MCP 管理和无限画布都以可启动的 DGOS 应用出现；它们可以是系统应用、第一方应用或第三方应用，但都遵守同一套 manifest、SDK、权限和生命周期规范。

| 应用类别 | 首批示例 | 运行边界 |
| --- | --- | --- |
| 系统应用 | 应用商店、文件、系统设置、开发者中心 | 由 DGOS 发行，负责系统管理入口，不绕过权限服务 |
| 平台控制面应用 | 应用目录、系统设置、开发者中心、Skill 管理、MCP 管理、系统智能助手 | 由 DGOS 发行，负责系统管理入口，不绕过权限服务 |
| 参考应用 | DGOS AI 工作台 | 由 DGOS 或官方团队发行，通过公开 DGOS API/SDK 使用 Provider 和 AI Task；真实模型调用必须经过 DGOS Provider Adapter |
| 第一方业务应用 | 文件、天气、对话智能体、无限画布等 | 按 V2–V6 分阶段接入，不因界面占位计入 V1 |
| 第三方应用 | 按规范发布的创作、数据或自动化应用 | 通过 manifest 声明权限和能力，不能读取其他应用私有数据 |
| 扩展能力 | Skill、MCP 服务、Canvas 节点、模板 | 可由应用目录单独发现或由管理应用安装；执行仍受 DGOS Extension Runtime 和权限服务约束 |

应用化不意味着所有能力使用同一种内部实现：用户看到的是统一的应用入口和窗口，系统内部仍可将 Skill、MCP 或节点作为受控扩展注册到相应运行时。应用商店负责发现、详情、安装、更新和卸载；DGOS Shell 负责启动、窗口和工作区；各应用负责自己的页面与业务交互。

### 8.1 用户端导航

桌面/启动台 → 应用商店或其他应用窗口 → DGOS 工作区/项目 → 画布、文件、对话、Skill/MCP 或设置；项目内以应用自己的页面承载配置、任务状态和产物。

### 8.2 管理端导航

DGOS 自有系统设置、应用商店/应用管理和开发者入口属于平台界面；系统级身份、模型、权限和发布管理不依赖 DX OS。各管理能力按版本范围逐步开放。

### 8.3 身份与组织演进

| 阶段 | 交付 | 约束 |
| --- | --- | --- |
| V1 | `UserProfile`、`Session`、主体作用域和受控本地/适配器会话 | 所有权限与资源归属使用 `subjectType/subjectId`；不把正式账号能力伪装成已完成 |
| V2 | 正式登录、登出、会话续期、个人数据归属和安全回跳 | 桌面/Web 共用身份 API，DGOS 平台适配层只负责安全存储和回调适配 |
| V3–V5 | 项目成员和共享资源的主体扩展预留 | 资源授权不能写死为单一用户字符串 |
| V6 | 组织、团队、成员角色、组织策略、共享开发和协作审计 | `organization`/`team` 成为可授权主体，支持成员变更和离职回收 |
